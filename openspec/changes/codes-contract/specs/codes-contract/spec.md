# codes-contract — контракт кода Tessera Codes

> **Переработано 2026-08-19** под решения D20–D32 воркспейса (`codes-phone-channel`):
> телефонный канал с человеком-оператором удалён, выдачу делает сервер, статический ключ
> устройства из вычисления кода исключён (эфемерный KEM), гибридный nonce со счётчиком
> упразднён, квитанции заменены грантами.

## ADDED Requirements

### Requirement: Каноническая сериализация
Крейт ДОЛЖЕН (MUST) предоставлять единственную реализацию канонической сериализации входа
MAC: конкатенация полей в фиксированном порядке `№ устройства, эпоха, nonce, role_id,
level, личный номер инженера`, где каждое поле кодируется как длина `u32` big-endian,
затем байты значения; строки — UTF-8 в нормализации NFC, числа — фиксированной ширины
big-endian. Номер устройства ДОЛЖЕН (MUST) входить в канонизацию значимыми символами (в
форме, по которой считается контрольный символ), а не в том написании, в каком он
напечатан: разделители и регистр не меняют номера, и два написания одного номера обязаны
давать один код. Тип входа канонизации НЕ ДОЛЖЕН (MUST NOT) принимать номер произвольной
строкой — иначе выбор написания достаётся вызывающему, и устройство с сервером разойдутся
в байтах. Порядок и кодировка НЕ ДОЛЖНЫ (MUST NOT) выводиться из порядка полей структур
Rust или из производных реализаций сериализации. Байты канонизации ДОЛЖНЫ (MUST) быть
закреплены голден-векторами в репозитории, проверяемыми и нативной, и WASM-сборкой.

Личный номер инженера входит в канонизацию ОБЯЗАТЕЛЬНО (MUST): он делает код непригодным
под чужим именем и позволяет устройству назвать входившего в собственном журнале, не
дожидаясь выгрузки серверных логов.

#### Scenario: Перестановка полей структуры не меняет байты
- **WHEN** порядок полей во внутренней структуре Rust изменён рефакторингом
- **THEN** байты канонизации остаются прежними, и голден-тесты проходят

#### Scenario: Два написания одного номера
- **WHEN** номер устройства подан с разделителями и в нижнем регистре, а затем без
  разделителей и в верхнем
- **THEN** байты канонизации совпадают, и обе стороны получают один и тот же код

#### Scenario: Код под чужим именем
- **WHEN** код вычислен для одного личного номера инженера, а предъявлен в попытке,
  где заявлен другой
- **THEN** канонизация даёт другие байты, MAC не сходится, вход отклоняется

#### Scenario: Паритет натив ↔ WASM
- **WHEN** голден-векторы прогоняются нативной сборкой и сборкой `wasm32-unknown-unknown`
- **THEN** обе дают идентичные байты канонизации, идентичный `K` и идентичный код;
  расхождение проваливает сборку

### Requirement: Вывод общего ключа на эфемерном KEM
Крейт ДОЛЖЕН (MUST) выводить общий ключ `K = KDF(Z, № устройства ‖ hash(канонический
подписанный билет сервера))`, принимая `Z` (результат DH) снаружи. **`Z` ДОЛЖЕН (MUST)
вычисляться на ЭФЕМЕРНОЙ паре устройства и статическом ключе сервера выдачи; статический
ключ устройства в выводе `K` НЕ УЧАСТВУЕТ (MUST NOT)** — он служит только для подписи
challenge. Эфемерная пара порождается на каждую попытку, её приватная часть живёт лишь в
памяти устройства.

Крейт НЕ ДОЛЖЕН (MUST NOT) выполнять DH сам и НЕ ДОЛЖЕН (MUST NOT) содержать привязки к
PKCS#11 — реализация DH подаётся через trait. Реализация DH ДОЛЖНА (MUST) валидировать
публичную точку по правилам профиля (принадлежность кривой и подгруппе) до вычисления
`Z`; контракт ДОЛЖЕН (MUST) фиксировать это требование в документации trait'а. Материал
`Z`, `K` и эфемерный приватный ключ ДОЛЖНЫ (MUST) затираться при уничтожении.

Мотив исключения статического ключа: пока `K` выводился из него, всякий, кто знал ключ
устройства (подготовитель, снявший диск), вычислял коды за выдающую сторону. Эфемерная
пара закрывает это криптографически: приватной части будущей попытки не существует до её
начала.

#### Scenario: Подмена рамок билета меняет ключ
- **WHEN** любое поле билета сервера изменено после подписи
- **THEN** hash билета в контексте KDF отличается, `K` не совпадает и код не сходится
  (второй слой защиты; первый — проверка подписи билета потребителем)

#### Scenario: Знание статического ключа устройства не даёт кода
- **WHEN** злоумышленник располагает приватным ключом устройства (снятый диск, копия
  файла)
- **THEN** вычислить код он не может: `K` строится на эфемерной паре текущей попытки,
  которой у него нет; статический ключ позволяет лишь подписать challenge

### Requirement: Вычисление и сверка кода
Код ДОЛЖЕН (MUST) вычисляться как `truncate_N(HMAC(K, canon(...)))`. Алфавит кода ДОЛЖЕН
(MUST) быть параметром: Crockford base32 по умолчанию (основной способ ввода — обычная
клавиатура), десятичный профиль — явная конфигурация парков с ограниченным вводом.
Усечение ДОЛЖНО (MUST) быть равномерным по значению кода (без смещения от простого взятия
остатка на неполном диапазоне). Сверка кода ДОЛЖНА (MUST) выполняться за константное время
и возвращать единственную ошибку сверки без указания, какое поле или шаг не сошлись.

#### Scenario: Единая ошибка сверки
- **WHEN** код не сходится из-за неверной роли, неверного nonce, чужого личного номера
  или неверного `K`
- **THEN** вызывающему возвращается одна и та же ошибка сверки; причина уходит только
  в диагностический вывод потребителя

### Requirement: Параметры парка усиливаются только в строгую сторону
Параметры парка ДОЛЖНЫ (MUST) проверяться при разборе — длина кода, число попыток на
попытку входа, алфавит, максимальный TTL попытки, профиль алгоритма: значение слабее
минимума контракта ДОЛЖНО (MUST) приводить к ошибке разбора, а не к молчаливой
подстановке дефолта. Максимальный TTL попытки ДОЛЖЕН (MUST) быть нормативной константой
контракта (`MAX_ATTEMPT_TTL`) с проверкой `0 < ttl <= MAX_ATTEMPT_TTL`: без верхней
границы «только строже» ничего не ограничивает, а окно жизни status-token растягивается
на срок попытки. Сравнение двух наборов параметров ДОЛЖНО (MUST) быть частичным порядком:
набор считается усилением, только если не слабее по каждой координате.

Разрядность кода и предел попыток калибруются под клавиатурный ввод (base32 даёт ту же
стойкость короче десятичного) и фиксируются как нижняя граница контракта.

#### Scenario: Конфиг слабее минимума
- **WHEN** конфигурация парка задаёт код короче минимума контракта
- **THEN** разбор параметров возвращает ошибку, и объект параметров не создаётся

#### Scenario: TTL сверх нормативного максимума
- **WHEN** конфигурация задаёт срок жизни попытки больше `MAX_ATTEMPT_TTL`
- **THEN** разбор возвращает ошибку: верхняя граница задана контрактом и парком не
  ослабляется

#### Scenario: Размен строгости не является усилением
- **WHEN** конфигурация удлиняет код, но одновременно увеличивает число попыток
- **THEN** набор не признаётся усилением исходного, и сравнение это отражает

### Requirement: Nonce попытки — длинное случайное значение
Nonce ДОЛЖЕН (MUST) быть длинным значением CSPRNG фиксированной ширины профиля. Крейт НЕ
ДОЛЖЕН (MUST NOT) генерировать его сам — он принимается снаружи и проверяется на ширину и
алфавит. **Гибридный nonce (монотонный счётчик ‖ случайный хвост) УПРАЗДНЁН (MUST NOT):**
он существовал ради диктовки голосом, которой больше нет, и тянул за собой персистентный
счётчик, hard-refuse на опережение и детекцию запасания. Счётчика попыток в контракте нет,
переполнения — тоже.

Неповторяемость обеспечивается шириной случайного значения и тем, что состояние попытки
живёт только в памяти устройства: перезагрузка и откат снимка без памяти гасят попытку.

#### Scenario: Короткий или предсказуемый nonce
- **WHEN** потребитель подаёт nonce меньшей ширины либо не из CSPRNG-источника по
  объявленному профилю
- **THEN** разбор возвращает ошибку: контракт не принимает значения, не удовлетворяющие
  профилю ширины

### Requirement: Форматы документов канала
Крейт ДОЛЖЕН (MUST) предоставлять разбор, сериализацию и проверку структуры для:

- **билета сервера** `{ид сервера, публичный ключ, рамки (теги/регион, максимальный
  уровень, непустой перечень ролей), срок, номер}`;
- **записи реестра устройства** `record_payload` `{№, публичный ключ, эпоха, серийники,
  уровень защиты ключа, наличие и тип монотонного якоря, партия, отпечаток базовой линии}`
  плюс три подписи в фиксированном порядке: PoP устройства по payload, подпись
  организации по `payload ‖ PoP`, подпись владельца по digest всего предыдущего;
- **записи реестра инженера** `{идентификатор, публичный ключ аутентификатора,
  организация, подпись организации, PoP}` и авторизации инженера `{идентификатор,
  организация, отпечаток ключа, рамки, срок}`;
- **подписанного запроса инженера** — единый канонический объект `{полный challenge,
  идентификатор инженера, основание, время, digest политики четырёх глаз}`;
  авторизационные поля (устройство, роль, уровень) существуют в нём в ЕДИНСТВЕННОМ
  экземпляре, внутри challenge, и НЕ ДОЛЖНЫ (MUST NOT) дублироваться рядом;
- **гранта** `{подписанный запрос инженера, подпись сервера, при необходимости подпись
  подтверждающего}`; любые продублированные снаружи поля ДОЛЖНЫ (MUST) проверяться на
  побайтовое равенство с подписанными;
- **status-token** `{идентификатор ключа status-службы, nonce попытки, отпечаток ключа
  инженера, digest авторизации, голова списка отзывов, статус, срок}`;
- **challenge** `{№ с контрольным символом, эпоха, nonce, role_id, level, личный номер
  инженера, эфемерная публичная точка}` с подписью ключа устройства.

Проверка подписей ДОЛЖНА (MUST) выполняться через trait верификатора; крейт НЕ ДОЛЖЕН
(MUST NOT) содержать собственного хранилища якорей доверия. Разбор ДОЛЖЕН (MUST) быть
строгим: неизвестные поля, битая структура, недопустимые значения — ошибка, а не
игнорирование. **Формат квитанции оператора УДАЛЁН (MUST NOT):** выдающая сторона —
сервер, и факт выдачи выражается грантом с вложенной подписью инженера.

#### Scenario: Неизвестное поле в билете
- **WHEN** билет содержит поле, не описанное форматом текущей версии контракта
- **THEN** разбор завершается ошибкой (fail-closed), а не отбрасывает поле молча

#### Scenario: Расхождение продублированного поля
- **WHEN** во внешней части гранта роль или основание отличается от подписанного
  инженером значения
- **THEN** проверка структуры возвращает ошибку: побайтовое равенство обязательно

#### Scenario: Основание запроса обязательно
- **WHEN** собирается запрос без заполненного основания
- **THEN** сборка возвращает ошибку — запрос без основания не является валидным
  документом контракта

### Requirement: Профиль алгоритма и гейт ГОСТ
Профиль алгоритма пары ДОЛЖЕН (MUST) быть параметром контракта: P-256 (дефолт
международного профиля), ГОСТ VKO 34.10-2012 (профиль РФ), X25519 (опция).
ГОСТ-профиль ДОЛЖЕН (MUST) быть помечен в API как неподтверждённый до закрытия
вендорского гейта; включение парка на неподтверждённом профиле ДОЛЖНО (MUST) требовать
явного признака в конфигурации, а не проходить по умолчанию.

#### Scenario: Запуск на неподтверждённом профиле
- **WHEN** конфигурация парка выбирает ГОСТ-профиль без явного признака принятия риска
- **THEN** разбор параметров возвращает ошибку с указанием на открытый гейт
