# codes-contract — контракт кода Tessera Codes

## ADDED Requirements

### Requirement: Каноническая сериализация
Крейт ДОЛЖЕН (MUST) предоставлять единственную реализацию канонической сериализации входа
MAC: конкатенация полей в фиксированном порядке `№ устройства, nonce, role_id, level`, где
каждое поле кодируется как длина `u32` big-endian, затем байты значения; строки — UTF-8 в
нормализации NFC, числа — фиксированной ширины big-endian. Номер устройства ДОЛЖЕН (MUST)
входить в канонизацию значимыми символами (в форме, по которой считается контрольный
символ), а не в том написании, в каком он напечатан: разделители и регистр не меняют
номера, и два написания одного номера обязаны давать один код. Тип входа канонизации
НЕ ДОЛЖЕН (MUST NOT) принимать номер произвольной строкой — иначе выбор написания
достаётся вызывающему, и устройство с кабинетом разойдутся в байтах. Порядок и кодировка НЕ ДОЛЖНЫ
(MUST NOT) выводиться из порядка полей структур Rust или из производных реализаций
сериализации. Байты канонизации ДОЛЖНЫ (MUST) быть закреплены голден-векторами в
репозитории, проверяемыми и нативной, и WASM-сборкой.

#### Scenario: Перестановка полей структуры не меняет байты
- **WHEN** порядок полей во внутренней структуре Rust изменён рефакторингом
- **THEN** байты канонизации остаются прежними, и голден-тесты проходят

#### Scenario: Два написания одного номера
- **WHEN** номер устройства подан с разделителями и в нижнем регистре, а затем без
  разделителей и в верхнем
- **THEN** байты канонизации совпадают, и обе стороны получают один и тот же код

#### Scenario: Паритет натив ↔ WASM
- **WHEN** голден-векторы прогоняются нативной сборкой и сборкой `wasm32-unknown-unknown`
- **THEN** обе дают идентичные байты канонизации, идентичный `K` и идентичный код;
  расхождение проваливает сборку

### Requirement: Вывод общего ключа
Крейт ДОЛЖЕН (MUST) выводить общий ключ `K = KDF(Z, № устройства ‖ эпоха ‖ hash(канонический
подписанный билет))`, принимая `Z` (результат DH) снаружи. Крейт НЕ ДОЛЖЕН (MUST NOT)
выполнять DH сам и НЕ ДОЛЖЕН (MUST NOT) содержать привязки к PKCS#11 — реализация DH
подаётся через trait. Реализация DH ДОЛЖНА (MUST) валидировать публичную точку по правилам
профиля (принадлежность кривой и подгруппе) до вычисления `Z`; контракт ДОЛЖЕН (MUST)
фиксировать это требование в документации trait'а. Материал `Z` и `K` ДОЛЖЕН (MUST)
затираться при уничтожении.

#### Scenario: Подмена рамок билета меняет ключ
- **WHEN** любое поле билета изменено после подписи
- **THEN** hash билета в контексте KDF отличается, `K` не совпадает и код не сходится
  (второй слой защиты; первый — проверка подписи билета потребителем)

#### Scenario: Смена эпохи разводит ключи
- **WHEN** устройство получило новую пару и эпоха увеличена
- **THEN** `K` новой эпохи не совпадает с `K` старой при том же `Z`, и коды старой эпохи
  не верифицируются

### Requirement: Вычисление и сверка кода
Код ДОЛЖЕН (MUST) вычисляться как `truncate_N(HMAC(K, canon(...)))`. Алфавит кода ДОЛЖЕН
(MUST) быть параметром: десятичные цифры по умолчанию, Crockford base32 — опция.
Усечение ДОЛЖНО (MUST) быть равномерным по значению кода (без смещения от простого взятия
остатка на неполном диапазоне). Сверка кода ДОЛЖНА (MUST) выполняться за константное время
и возвращать единственную ошибку сверки без указания, какое поле или шаг не сошлись.

#### Scenario: Единая ошибка сверки
- **WHEN** код не сходится из-за неверной роли, неверного nonce или неверного `K`
- **THEN** вызывающему возвращается одна и та же ошибка сверки; причина уходит только
  в диагностический вывод потребителя

### Requirement: Параметры парка усиливаются только в строгую сторону
Параметры парка ДОЛЖНЫ (MUST) проверяться при разборе — длина кода, число попыток на nonce,
алфавит, ширина счётчика и случайного хвоста, профиль алгоритма, режим временного слота:
значение слабее минимума контракта (код короче 6 цифр, попыток больше 10) ДОЛЖНО (MUST)
приводить к ошибке разбора, а не к молчаливой подстановке дефолта. Дефолты — код 8 цифр,
5 попыток. Сравнение двух наборов параметров ДОЛЖНО (MUST) быть частичным порядком:
набор считается усилением, только если не слабее по каждой координате.

#### Scenario: Конфиг слабее минимума
- **WHEN** конфигурация парка задаёт код в 4 цифры
- **THEN** разбор параметров возвращает ошибку, и объект параметров не создаётся

#### Scenario: Размен строгости не является усилением
- **WHEN** конфигурация удлиняет код, но одновременно увеличивает число попыток
- **THEN** набор не признаётся усилением исходного, и сравнение это отражает

### Requirement: Гибридный nonce
Nonce телефонного канала ДОЛЖЕН (MUST) быть типом с разбором и сборкой: монотонный
десятичный счётчик фиксированной ширины профиля, за ним случайный хвост фиксированной
ширины. Крейт НЕ ДОЛЖЕН (MUST NOT) генерировать случайный хвост сам — он принимается
снаружи и проверяется на ширину и алфавит. Переполнение счётчика ДОЛЖНО (MUST) возвращаться
отдельной ошибкой, отличимой от прочих, и НЕ ДОЛЖНО (MUST NOT) переноситься по модулю.

#### Scenario: Переполнение счётчика
- **WHEN** счётчик достиг предела ширины профиля
- **THEN** сборка следующего nonce возвращает ошибку переполнения, по которой потребитель
  инициирует смену эпохи ключа, а не продолжает выдачу

### Requirement: Форматы документов канала
Крейт ДОЛЖЕН (MUST) предоставлять разбор, сериализацию и проверку структуры для: билета
оператора `{ид оператора, публичный ключ, рамки (теги/регион, максимальный уровень,
непустой перечень ролей), срок, номер}`, записи реестра устройства
`{№, публичный ключ, эпоха, организация, подпись организации, PoP-подпись}`, квитанции о
выдаче `{№, эпоха, nonce, role_id, level, время, основание}` и challenge телефонного канала
`{№ с контрольным символом, эпоха, nonce, role_id, level, ид оператора}`. Проверка подписей
ДОЛЖНА (MUST) выполняться через trait верификатора; крейт НЕ ДОЛЖЕН (MUST NOT) содержать
собственного хранилища якорей доверия. Разбор ДОЛЖЕН (MUST) быть строгим: неизвестные поля,
битая структура, недопустимые значения — ошибка, а не игнорирование.

#### Scenario: Неизвестное поле в билете
- **WHEN** билет содержит поле, не описанное форматом текущей версии контракта
- **THEN** разбор завершается ошибкой (fail-closed), а не отбрасывает поле молча

#### Scenario: Основание квитанции обязательно
- **WHEN** собирается квитанция без заполненного основания
- **THEN** сборка возвращает ошибку — квитанция без основания не является валидным
  документом контракта

### Requirement: Профиль алгоритма и гейт ГОСТ
Профиль алгоритма пары ДОЛЖЕН (MUST) быть параметром контракта: P-256 (дефолт
международного профиля), ГОСТ VKO 34.10-2012 (профиль РФ), X25519 (опция).
ГОСТ-профиль ДОЛЖЕН (MUST) быть помечен в API как неподтверждённый до закрытия
вендорского гейта; включение парка на неподтверждённом профиле ДОЛЖНО (MUST) требовать
явного признака в конфигурации, а не проходить по умолчанию.

#### Scenario: Запуск на неподтверждённом профиле
- **WHEN** конфигурация парка выбирает ГОСТ-профиль без явного признака принятия риска
- **THEN** разбор параметров возвращает ошибку с указанием на открытый гейт
