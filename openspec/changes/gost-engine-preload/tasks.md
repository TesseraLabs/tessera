## 0. Диагноз (до всякого кода)

- [x] 0.1 **ПОДТВЕРЖДЕНО на стенде 2026-08-10/11.** Отказ `ENGINE_ctrl_cmd_string sequence (SO_PATH=1, ID=1, LOAD=0)` воспроизведён на Astra 1.8.4 (стенд профиля `astra-vm`) с реальным ГОСТ-2012-256 удостоверением. `clear_ambient_registration` находит ambient-запись и снимает её успешно (обе операции возвращают успех — видно по инструментированной сборке), следующий `LOAD` всё равно даёт `0`
- [x] 0.2 Fallback «подобрать уже зарегистрированный движок» реализован и проверен на стенде — **не работает**: `by_id` отдаёт «no engine registered under id gost». Конфликта на уровне таблицы ENGINE в момент отказа нет, дело внутри движка. Код удалён полностью
- [x] 0.3 Первопричина найдена чтением исходников `gost-engine` (`gost_eng.c`, `check_gost_engine`): process-global guard `ameth_GostR3410_2001` выставляется при первой успешной инициализации, и `check_gost_engine` при непустом значении печатает `GOST engine already loaded` и отказывает. **Уточнено по v3.0.3 (2026-08-16):** `gost_engine_destroy` флаг всё-таки обнуляет — `ameth_GostR3410_2001` лежит первым элементом `gost_meth_array` (`gost_eng.c:118`), а цикл деструктора зануляет `*minfo->ameth` у всех элементов. Прежняя формулировка «чистит таблицу методов, но не флаг» неверна. Практический вывод не меняется: пока движок зарегистрирован в libcrypto, деструктор не вызывается, и повторная инициализация в том же процессе не проходит
- [x] 0.4 Модель процессов объясняет плавающую воспроизводимость: `sudo`/`login`/`sshd` живут одну попытку входа (гонки нет), `fly-dm` — один процесс на весь uptime дисплея (движок либо загрузился первым входом, либо сломан до перезапуска службы)
- [x] 0.5 NID сверены с `obj_mac.h`: Streebog-256/512 = `982`/`983` (`md_gost12_256`/`md_gost12_512`); захардкоженные в модуле `1177`/`1178` = `kuznyechik_ctr_acpkm` / `kuznyechik_ctr_acpkm_omac`, шифр «Кузнечик»

## 1. Загрузка движка

- [x] 1.1 Гейт `self_check` расширен с `needs_gost()` на `gost_engine_path.is_some()`. **Обоснование уточнено после ревью:** движок нужен и там, где ГОСТ-OID в allow-list нет вовсе — алгоритм ответа на challenge выбирается по NID публичного ключа листа, а контейнер под ГОСТ-PBE перечитывается после загрузки движка. Прежняя формулировка «становится первым обращением к libcrypto в процессе» неверна: модуль работает внутри чужого процесса, который трогает libcrypto раньше PAM-стека. Это самая ранняя точка, которую контролирует продукт
- [x] 1.2 `ensure_loaded_if_any_gost` (путь верификации цепочки) не тронут — остаётся ленивым
- [x] 1.3 Устройство без `gost_engine_path` движок не трогает: RSA-only сценарий сохранён
- [x] 1.4 Проверено на стенде: `no pre-existing registration found` → `load_rc=1` → полный цикл `pamtester fly-dm serv authenticate acct_mgmt open_session close_session`, дважды подряд
- [x] 1.5 Проверено сильнее `pamtester`: реальный интерактивный вход в `fly-dm` с USB-носителя (privilege separation, не один процесс на весь диалог)
- [x] 1.6 Изолирующая проверка: с пустым allow-list движок грузится так же (`load_rc=1`), а отказ приходит позже, на проверке allow-list, — значит загрузка и allow-list развязаны

## 6. Правки по ревью PR #94

- [ ] 6.1 Префлайт грузит движок во ВСЕХ ветках с заданным путём. Прежде ветки `mode = "pkcs11"` и «путь задан, ГОСТ не разрешён» возвращались с WARN и exit 0, тогда как аутентификация грузила движок, — `tessera check` как `ExecStartPre` пропускал машину, где не входит никто
- [ ] 6.2 Запись про пару режима и бэкенда: WARN → ERROR и переименование `gost_pkcs11_unsupported` → `pkcs11_openssl_unsupported`. Причина шире ГОСТ: при `mode = "pkcs11"` + `crypto_backend = "openssl"` аутентификация возвращает `Pkcs11OpensslEngineNotImplemented` для любого удостоверения
- [ ] 6.3 Единая функция готовности вместо двух расходящихся проверок: загрузка + резолюция обоих дайджестов, один вызов из `self_check` и из префлайта
- [ ] 6.4 ГОСТ-preload переставлен перед `self_check_pkcs11`: вендорский модуль при `C_Initialize` может через `openssl.cnf` вызвать ambient-регистрацию. Сужение окна, не гарантия
- [ ] 6.5 Комментарий в `algorithms.rs` говорит прямо, что литерал `1177` был неверен (это «Кузнечик»), а не «стабилен, но лучше избегать». Добавлено покрытие, работающее без движка: `Nid::from_raw(1177)` не даёт 32-байтовый дайджест, имена равны SN у NID 982/983
- [ ] 6.6 Обоснование отказа ГОСТ через токен переписано: проект на `cryptoki` 0.12, где `Mechanism::VendorDefined` есть, но `MechanismType::new_vendor_defined` отвергает значения ниже `CKM_VENDOR_DEFINED` (0x8000_0000), а ГОСТ-механизмы стандартные (`CKM_GOSTR3410` = 0x1201, `CKM_GOSTR3411` = 0x1210); в `cryptoki-sys` GOST-констант нет
- [ ] 6.7 Тесты `gost.rs` переименованы под нумерацию случаев 1-4; добавлен тест на комбинацию «путь задан, ГОСТ не разрешён, движок неисправен»
- [ ] 6.8 Документация: убраны утверждения «первым трогает libcrypto» и «движок никогда не будет загружен»; исправлено противоречие `[engine_section]`/`[gost_section]`; описание guard'а приведено к исходникам v3.0.3
- [ ] 6.9 `daemon`, `check` и `enroll` переведены на `load_privileged_validated_config`. Раз загрузка движка расширена на процессы CLI, а `try_load` зовёт `ENGINE_set_default(ENGINE_METHOD_ALL)`, путь к стороннему `.so` обязан проверяться так же строго, как в PAM. Новая логика не потребовалась: привилегированный загрузчик уже канонизирует `gost_engine_path` с проверкой root-владения. **Изменение fail-closed:** на машине, где конфиг или `.so` лежат не под root, демон и `tessera check` перестанут стартовать. `role` и `dump-host-id` не переключены — они движок не грузят
- [ ] 6.11 Проба движка выполняется раньше всего, что обращается к libcrypto, не только в `self_check`. Найдено независимым ревью тремя заходами подряд, каждый раз в новом месте: сначала префлайт против PAM, затем верификация MAC-плагина в `run_startup_checks`, затем верификация манифеста в управляемой выдаче — включая ветку, где первая загрузка конфигурации падает штатно (`[trust.revocation]` указывает на `device.crl`, который создаёт сам `install()`). Порядок фиксируется тестами с журналом вызовов, а не косвенными признаками
- [ ] 6.12 Привилегированная проверка `pkcs11_module` распространена на конфигурации, где модуль загружается при `mode = "pkcs12"` с `pkcs12_source = "token_object"`. Прежде загрузчик канонизировал путь только при `mode = "pkcs11"`, из-за чего заявленная гарантия «сторонний модуль в привилегированном процессе проверен» для этого носителя не выполнялась
- [ ] 6.13 Текст записи `gost_engine_load_failed` называет настоящий масштаб отказа: при неисправном движке самопроверка обрывается до разбора удостоверения, поэтому не проходит ни одна аутентификация, включая RSA и ECDSA. Прежняя формулировка говорила про «удостоверения, которым нужен движок» и преуменьшала последствия
- [ ] 6.10 Хелпер `config-mutate.sh`: добавлены режимы `gost-engine-unused-real` (настоящий движок при неразрешённых ГОСТ-подписях) и `gost-pkcs11-openssl`; поиск движка вынесен в `find_gost_engine`. Замена `mode` в новом режиме ограничена верхним уровнем — ключ с тем же именем есть в `[trust.revocation]`, и без оговорки правило переписывало бы режим отзыва

## 5a. Найдено попутно, не чинится здесь

- [ ] 5a.1 `engine.rs` при sanity-проверке после загрузки принимает `md_gost12_256` ИЛИ `streebog256` (форки именуют по-разному), а `algorithms.rs` резолвит только `md_gost12_256`/`md_gost12_512`. На форке со вторым именованием загрузка объявляется успешной, а первый запрос дайджеста отдаёт `DigestUnavailable`. Расхождение старше этого изменения; чинить без воспроизводящего кейса нельзя, а форка с таким именованием под рукой нет — ожидание пришлось бы сочинить
