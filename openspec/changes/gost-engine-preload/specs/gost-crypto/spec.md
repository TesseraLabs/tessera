## MODIFIED Requirements

### Requirement: Ленивая загрузка engine

Engine ДОЛЖЕН (MUST) загружаться once-per-process (OnceLock).

**Верификация цепочки остаётся ленивой.** `ensure_loaded_if_any_gost`
(engine.rs) ДОЛЖЕН (MUST) трогать engine только тогда, когда в цепочке есть
GOST-подписанный сертификат.

**Самопроверка грузит engine по конфигурации, а не по цепочке.**
`self_check` ДОЛЖЕН (MUST) выполнять загрузку, как только задан
`gost_engine_path`, — независимо от того, разрешает ли allow-list
ГОСТ-подписи и какая цепочка будет предъявлена.

Причина первая: allow-list подписей не описывает всех, кому нужен engine.
Алгоритм ответа на challenge выбирается по NID ПУБЛИЧНОГО КЛЮЧА листа,
поэтому ГОСТ-ключ в сертификате, подписанном RSA, — рабочее удостоверение
при пустом ГОСТ-allow-list'е. Контейнер под ГОСТ-PBE перечитывается после
загрузки движка независимо от того, чем подписаны сертификаты внутри.
Привязка загрузки к allow-list'у отказывала бы этим конфигурациям
детерминированно.

Причина вторая: `gost-engine` держит process-global guard, который
выставляется при первой успешной инициализации. Сбросить его мог бы
деструктор движка, но пока движок зарегистрирован в libcrypto, деструктор
не вызывается. Хост, прописавший engine в `openssl.cnf`
(`default_algorithms = ALL`, штатная конфигурация Astra), инициализирует его
при первом обращении к libcrypto в процессе, после чего повторная
инициализация не проходит — последовательность SO_PATH+ID+LOAD отдаёт
`LOAD=0`, и никакой вызов OpenSSL ENGINE API этого не исправляет.

Быть первым, кто трогает libcrypto в процессе, продукт НЕ МОЖЕТ: модуль
работает внутри чужого процесса, который обращается к libcrypto до
PAM-стека. Загрузка по факту заданного пути — самая ранняя точка, которую
продукт контролирует, и она сужает окно гонки, но не закрывает его.

Устройство, где `gost_engine_path` НЕ задан, engine затрагивать НЕ ДОЛЖНО
(MUST NOT) вовсе: терминальный RSA-only кейс работает без `gost-engine`.

Отказ загрузки ДОЛЖЕН (MUST) быть fail-closed.

#### Scenario: GOST-цепочка, engine не грузится
- **WHEN** предъявлена GOST-цепочка, engine отсутствует/сломан
- **THEN** `TrustError::EngineLoadFailed` → отказ верификации (fail-closed)

#### Scenario: Путь задан, engine грузится до всякой цепочки
- **WHEN** в конфигурации задан `gost_engine_path`
- **THEN** `self_check` грузит engine при аутентификации независимо от allow-list и предъявленной цепочки — в самой ранней точке процесса, которую контролирует продукт: до разбора контейнера и до инициализации вендорского PKCS#11-модуля

#### Scenario: ГОСТ-ключ в сертификате, подписанном другим алгоритмом
- **WHEN** задан `gost_engine_path`, ГОСТ-OID в allow-list отсутствует, предъявлено удостоверение с ГОСТ-ключом в сертификате, подписанном RSA
- **THEN** ответ на challenge считается ГОСТ-ключом на загруженном engine, а не отвергается как неподдерживаемый

#### Scenario: Путь не задан, engine не затрагивается
- **WHEN** `gost_engine_path` в конфигурации отсутствует
- **THEN** engine не грузится ни на одном пути; RSA/ECDSA-аутентификация проходит на устройстве без `gost-engine`

#### Scenario: Engine уже инициализирован хостом в этом процессе
- **WHEN** engine был инициализирован ambient-регистрацией (`openssl.cnf`) раньше tessera в том же процессе, и его загрузка отдаёт `LOAD=0`
- **THEN** аутентификация отказывает fail-closed; снятие ambient-регистрации средствами OpenSSL ENGINE API восстановить загрузку НЕ может — состояние неисправимо до завершения процесса

### Requirement: Алгоритмы

Модуль ДОЛЖЕН (MUST) поддерживать: GOST R 34.10-2012 256/512 (TC26 OID `1.2.643.7.1.1.3.2`/`3.3`), Streebog-256/512.

Streebog-дайджесты ДОЛЖНЫ (MUST) резолвиться **по имени**
(`EVP_get_digestbyname`, короткие имена libcrypto `md_gost12_256` /
`md_gost12_512`), а не по числовому NID, продублированному в коде рядом с
OID. Такое дублирование уже приводило к дефекту: модуль был захардкожен на
NID `1177`/`1178`, которые в `obj_mac.h` принадлежат
`kuznyechik_ctr_acpkm` и `kuznyechik_ctr_acpkm_omac` — шифру «Кузнечик», не
хешам; Streebog-256/512 это `982`/`983`.

Подпись GOST-цепочек верифицируется штатным `X509::verify` после установки engine default.

#### Scenario: Верификация GOST-цепочки
- **WHEN** предъявлена цепочка с GOST R 34.10-2012 (256 или 512) и engine установлен как default
- **THEN** подпись верифицируется штатным `X509::verify` с использованием Streebog-256/512

#### Scenario: Дайджест резолвится по имени
- **WHEN** engine загружен и требуется хендл Streebog-256 или Streebog-512
- **THEN** дайджест берётся по короткому имени libcrypto; числовой NID в коде не дублируется
