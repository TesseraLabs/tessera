## Context

Замеры на живом Рутокен Lite (`rtpkcs11ecp` 2.14.1, macOS, 2026-07-31), все через `pkcs11-tool`:

| Операция | Результат |
| --- | --- |
| Запись `CKO_CERTIFICATE` | успешно, объект читается |
| Запись приватного ключа RSA | `CKR_TEMPLATE_INCONSISTENT` — отказ |
| Запись `.p12` (2571 Б) объектом `CKO_DATA` | успешно, round-trip побайтово идентичен |
| Объект без `--private` | виден в `--list-objects` **без логина** |
| Объект с `--private` | без логина не виден вообще |
| `C_GetMechanismList` | пустой список — криптографии нет |

Потолок размера одного объекта данных, с проверкой чтением:

```
 4K … 32K  — OK round-trip
    48K    — записалось «успешно», прочиталось 32768 из 49152
    64K    — записалось «успешно», прочиталось 0
```

Ключевое: превышение лимита **не диагностируется кодом возврата**. `C_CreateObject` рапортует успех,
данные при этом усечены или потеряны.

Текущий `authenticate_pkcs12` (flow.rs:430–762) идёт по пути `wait_for_usb` → per-partition loop
(mount → discover → envelope). Для CCID-токена монтировать нечего.

## Goals / Non-Goals

**Goals:**

- Пассивный токен как носитель конверта PKCS#12: прочитать `.p12` с токена и пойти дальше по уже
  существующему пути аутентификации.
- Честная фиксация уровня доверия: этот носитель слабее режима B и не должен подаваться иначе.
- Защита от молчаливого усечения при записи контейнера на токен.

**Non-Goals:**

- Подпись на пассивном токене — невозможна физически, режим B остаётся прерогативой активных
  токенов (ЭЦП 2.0/3.0, JaCarta-2 GOST).
- Хранение приватного ключа объектом ключа на пассивном токене — отвергается устройством.
- Замена mass-storage-пути: раздел на USB остаётся полноправным источником.
- Поддержка payload (CRL, конфиги, deb) на токене — отдельная работа, здесь только конверт.

## Decisions

### Решение 1: источник конверта, а не третий режим

Режимов аутентификации остаётся два. Вводится выбор источника внутри `mode = "pkcs12"`:
раздел USB-носителя (по умолчанию) либо объект данных на токене. Так сохраняется вся логика после
получения конверта — PIN-loop, challenge-response, сборка цепи, host_binding — и не плодится
комбинаторика режимов.

Альтернатива «`mode = "pkcs12_token"`» отвергнута: третий режим потянул бы дублирование ветки
`authenticate_*` и новую строку в матрице соответствий FlowError → PAM-код ради одного отличия во
входной точке.

### Решение 2: конверт на токене ОБЯЗАН быть приватным объектом

Читаем только объекты с `CKA_PRIVATE = true`. Публичный объект данных с конвертом игнорируется с
диагностикой, а не используется молча: дефолт `pkcs11-tool` (и, вероятно, стороннего инструментария)
делает объект публичным, то есть контейнер с извлекаемым ключом лежал бы читаемым без PIN. Мы не
можем помешать оператору записать его так, но обязаны отказаться такое принимать.

### Решение 3: запись верифицируется чтением, всегда

Инструмент выпуска после `C_CreateObject` перечитывает объект и сравнивает с исходником. Это
единственный способ отличить успешную запись от молчаливого усечения на 32 КБ. Дополнительно —
предварительная проверка размера с явной ошибкой до записи.

Порог не хардкодим числом 32 КБ как универсальный: измерен один экземпляр одной модели. Проверка
чтением корректна для любого лимита, включая неизвестный.

### Решение 4: уровень доверия — часть спеки, а не примечание в документации

Требование прямо фиксирует: ключ извлекаемый, подпись на хосте, защита эквивалентна «флешка + PIN».
Иначе различие между этим носителем и режимом B неизбежно размоется в документации и деках — риск
тем выше, что внешне это «вход по токену».

## Risks / Trade-offs

- **Носитель выглядит как режим B, но слабее** → явное требование в спеке, отдельная формулировка в
  документации, запрет называть это аппаратной защитой ключа в маркетинговых материалах.
- **Молчаливое усечение при записи** → обязательная верификация чтением плюс проверка размера до
  записи.
- **Оператор запишет конверт публичным объектом** → чтение отвергает не-приватные объекты.
- **Лимит измерен на одной модели** → не хардкодим порог как истину, полагаемся на верификацию.
- **Расширяется поверхность PKCS#11-слоя** (чтение `CKO_DATA`) → изменения ложатся поверх
  process-глобального контекста из `pkcs11-init-singleton`; порядок работ имеет значение.

## Migration Plan

1. Change реализуется **после** `pkcs11-init-singleton`: тот меняет владение контекстом в
   `backend.rs`, и делать обе правки одновременно — лишние конфликты.
2. Существующие инсталляции не затрагиваются: источник по умолчанию — раздел USB-носителя.
3. Откат: убрать ветку источника; носитель перестаёт поддерживаться, mass-storage-путь не страдает.

## Open Questions

1. Тот же ли лимит у других пассивных моделей (Рутокен Lite иных ревизий, JaCarta без крипты) —
   проверяется по мере появления железа.
2. Нужен ли перенос payload (CRL, конфиги) на токен тем же механизмом, или payload остаётся
   привилегией комбо-токенов с flash — решается вместе с issuer-tooling.
3. Ведёт ли себя активный токен (ЭЦП 3.0, в пути) так же в части объектов данных — стоит
   перепроверить, когда приедет.
4. Нужно ли инструменту выпуска уметь стирать старый конверт с токена перед записью нового
   (ротация удостоверения).
