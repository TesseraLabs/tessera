## 1. Формат и запись

- [x] 1.1 Общий формат записи с `issuance-journal`: выделить в переиспользуемый модуль/крейт, а не писать вторую реализацию
  — крейт `crates/tessera_hashchain` (обрамление строки, пересчёт цепочки, учёт заверений,
  общие полезные нагрузки `HeadSignature`/`Annotation`); `tessera_issuer::journal` переписан
  на него, формат на диске не изменился (та же genesis-преамбула, те же поля, тот же порядок).
- [x] 1.2 Запись события: `seq`, `prev_hash`, тип, поля, метка времени; genesis — фиксированное значение
  — `tessera_core::audit::AuditRecord`, преамбула `tessera-device-audit/v1/genesis`.
- [x] 1.3 Политика недоступности журнала по типу события: fail-closed до действия, эскалация постфактум
  — `AuditRecord::write_discipline()` + `audit::sink::{record, record_required, mirror}`.
  Граница подключена: `codes::audit::emit_success` возвращает `Result`, и в
  `pam_tessera::codes_flow::authenticate_by_code` его отказ становится
  `CodeFlowError::Unaccountable` (`PAM_PERM_DENIED`, 6) последним шагом перед выдачей
  сессии. Устройство без цепочки не отказывает — `sink::record_required` различает
  «цепочки нет» и «цепочка есть и запись не взяла» в одном месте.
  Журнал открывается и ставится в процесс из конфигурации ДО аутентификации:
  `sink::install_from_config` зовётся из `pam_sm_authenticate` (и из демона). Без этого
  вызова весь контур был мёртв на живом устройстве — цепочки в процессе не было, поэтому
  `record_required` возвращал `Ok` не потому, что журнал взял запись, а потому что журнала
  не было вовсе. Нашло обязательное ревью (C1).
  Тесты: `codes_flow::live_tests::fail_closed` — четыре случая, и **все ставят журнал
  только через `install_from_config`**, как это делает устройство; ручного `sink::install`
  в тестах не осталось. Проверено снятием обвязки: без `.map_err(...)?` краснеет тест про
  отказ, без установки внутри `install_from_config` краснеют два теста.
- [x] 1.4 Фильтр секретов на входе в журнал (общий с `logging-audit`), тесты на каждый класс чувствительных полей
  — `tessera_core::audit::secrets`, тест `every_class_of_secret_is_refused` (что человек вводит,
  код и всё производное от него, ключевой материал и контейнеры, предъявительский материал)
  плюс обратный тест `ordinary_fields_are_not_refused`. Записи фиксированной формы проверены
  тем же фильтром (`no_fixed_record_carries_a_field_the_secret_filter_would_refuse`).

## 3. Аннотации и потолок

- [x] 3.1 Запись-аннотация: пространство имён, данные-объект, включение в цепочку
  — `AuditJournal::annotate`, `tessera audit annotate`; ядро содержимое не читает.
- [x] 3.2 Потолок объёма как параметр конфигурации; явное событие «журнал заполнен»
  — секция `[audit]` в `config.toml`: `enabled`, `file`, `ceiling_bytes` (по умолчанию
  64 МиБ), `when_full`, `attest_interval_seconds`. Запись `journal_full` идёт в саму
  цепочку плюс диагностика в `tessera.audit_chain`.
  `enabled` не задан — следует за `[codes].enabled`: контроль над оператором телефонного
  канала держится на сверке, которую делает возможной этот журнал, поэтому устройство,
  предлагающее метод без журнала, сломано так, как само обнаружить не может. Устройства,
  никогда не включавшие метод, остаются как были — поэтому не просто `true` по умолчанию.
- [x] 3.3 Режимы при заполнении: отказ новых записей либо ротация с записью об обрыве; молчаливой ротации нет
  — `WhenFull::{Refuse, Rotate}`; при ротации новая цепочка ОТКРЫВАЕТСЯ записью `chain_break`
  (голова отставленной цепочки, число её строк, путь). Вторая ротация поверх ещё не вывезенной
  первой отвергается, а не затирает её.
- [x] 3.4 Тесты на достижение потолка в обоих режимах
  — `a_journal_at_its_ceiling_says_so_and_then_refuses`, `rotation_leaves_a_record_of_the_break`,
  `a_second_rotation_refuses_rather_than_overwriting_the_first`.

## 4. Интеграция с событиями

- [x] 4.1 `logging-audit`: события входа по коду, билетов, enrollment дублируются в цепочку
  — `codes::audit::{emit_success, emit_denied, emit_attempts_exhausted}` и
  `enrollment::audit::{emit_device_enrolled_full, emit_enrollment_rejected_full}` зеркалят
  событие в `audit::sink`. Отдельного события билетов в продукте нет: исход билета приезжает
  полем `reason` того же `qr_code_login` (`ticket_*`), и в цепочку он попадает вместе с ним.
- [x] 4.2 Проверка, что дублирование не меняет существующие tracing-targets (обратная совместимость потребителей)
  — `crates/tessera_core/tests/audit_chain_targets.rs`: пять событий снимаются подписчиком и
  сравниваются с эталоном (target + имя события + полный набор полей) в трёх состояниях —
  без цепочки, с цепочкой, снова без неё.

## 5. Приёмка

- [x] 5.1 E2E-кейсы в `tests/e2e/cases/`: вырезанная запись обнаруживается верификацией; журнал заполнен виден явно
  — `tests/e2e/cases/29-audit-chain.yaml`, кейсы AUD-001…AUD-005 плюс хелпер
  `tests/e2e/helpers/audit-fill.sh`. Ожидания сняты с локального прогона `tessera audit`.
  Стенд ставит `.deb` из main, где подкоманды `audit` ещё нет, поэтому suite красный —
  причина записана в `tests/e2e/BASELINE.md`.
- [x] 5.2 `cargo clippy --all-features` и дефолтная сборка чисты
  — обе чисты по затронутым крейтам. Остаётся один pedantic-warning в
  `crates/tessera_cli/src/enroll.rs:363` (`items_after_statements`) — он из незакоммиченной
  работы другого агента, не из этой.
- [x] 5.4 Второе ревью: пять блокирующих закрыты — гонка одновременных дописываний
  (блокировка на всю транзакцию, тест на 8 параллельных писателей краснеет при снятом
  хвате), криптографическая проверка заверения (`audit verify --attestation-key`,
  тест с переписанной историей и выдуманной подписью), синхронизация записи на диск
  (одна запись + `sync_data`, fsync каталога при создании), откат неудавшейся ротации,
  установка журнала в бою. Плюс: тесты крейта собираются без `--all-features`, открытие
  журнала читает файл один раз с конца вместо трёх полных чтений, потолок считает длину
  входящей записи, наблюдаемость выключенной цепочки, обе genesis-преамбулы переехали
  в `tessera_hashchain::domain`.
- [ ] 5.3 Замер объёма на профиле безлюдного устройства — сверить с бюджетом вывоза (`audit-export`)
  — не сделано: замер требует прогона на стенде, а стенда с этим кодом нет (см. 5.1).
  Порядок величины из формата известен: строка входа по коду — около 230 байт, так что
  дефолтный потолок 64 МиБ ловит разогнавшегося писателя, а не обычную работу. Настоящую
  цифру даст первый прогон после мержа.
