# Design: rescue-channel-hardening

## Context

Rescue/emergency-режимы systemd аутентифицируются `sulogin` (util-linux),
который читает `/etc/shadow` напрямую и **не** использует PAM — намеренный
upstream-дизайн (минимум зависимостей в канале последней инстанции).
На рекомендуемой конфигурации Tessera (root заблокирован, `*` в shadow)
rescue-диалог закрыт: `sulogin` отказывает («root account is locked»).
Стенд Astra SE 1.8.4 подтвердил: shadow `root:*`, стоковые
`rescue.service`/`emergency.service`, непатченный `sulogin` (Debian-ветка,
без Ubuntu-патча), пароль GRUB установлен (`superusers` + `password_pbkdf2`
через `/etc/grub.d/01_users` + `/boot/grub/user.cfg`), recovery-пункт меню
`--unrestricted`, `/boot/grub/user.cfg` world-readable (0644).

Закрытость канала — совокупность независимых фактов, любой из которых
меняется одной строкой без следа. Восстановление при закрытом канале —
две внеполосные лестницы (пароль GRUB + `init=/bin/bash`; внешний
носитель + recovery-ключ LUKS), обе требуют организационно зафиксированных
секретов. Rescue/emergency-загрузки не оставляют события в аудите Tessera.

Инфраструктура, на которую ложится change:

- пайплайн `startup_check` (`tessera_cli/src/startup_check.rs`):
  модули-проверки со `StartupCheckRecord` (Info/Warn/Error), общий для
  `tessera check` и старта демона;
- стабильные tracing-targets аудита (`mac.audit`, `role.audit`) —
  прецедент для нового target.

## Goals / Non-Goals

**Goals:**

- Согласованная advisory-диагностика закрытости rescue-канала
  (4 проверки `rescue_*`) в существующем пайплайне.
- Тамper-evidence: rescue/emergency-загрузка устройства становится
  событием аудита при следующем штатном старте monitord.
- Документированная рекомендуемая конфигурация и точная процедура
  восстановления (обе лестницы) в docs RU/EN.
- Threat-model: принцип независимости канала восстановления зафиксирован
  как MUST NOT-инвариант; T8 обновлён.

**Non-Goals:**

- Аутентификация Tessera внутри rescue (PAM-шелл вместо `sulogin`,
  вытягивание `pcscd` в rescue.target) — отвергнуто: общая мода отказа
  с восстанавливаемой подсистемой; в `rescue.target` нет `sockets.target`,
  PC/SC штатно недоступен.
- Привязка токена к LUKS (`systemd-cryptenroll --pkcs11-token-uri`) —
  отдельный будущий change (свой анти-lockout-контур: recovery-ключ,
  enrollment-процедура).
- Enforcement состояния (блокировка root, установка пароля GRUB,
  chmod `user.cfg`) — предмет провижининга образа; Tessera только
  диагностирует.
- Изменение поведения systemd в emergency (авто-ребут и т.п.) —
  только документируем останов как fail-closed.

## Decisions

### D1. Все проверки `rescue_*` — advisory (максимум WARN), не Error

Error в пайплайне = демон не стартует. Открытый rescue-канал не делает
демон неработоспособным или небезопасным для запуска; отказ демона
стартовать из-за политики хоста сам создаёт lockout входа по удостоверению —
ровно T8, от которого защищаемся. Даже пустое поле пароля root (свободный
консольный шелл) — дыра хоста, а не инвалидность Tessera: это WARN
с максимально жёсткой формулировкой.

Альтернатива (Error для пустого поля/`SULOGIN_FORCE`) отвергнута:
Tessera не вправе останавливать аутентификацию парка из-за политики,
которой владеет администратор образа.

### D2. Семантика четырёх проверок

| Check id | INFO | WARN |
|---|---|---|
| `rescue_root_locked` | поле `!`/`!!`/`*` (диалог закрыт) | хеш («rescue-диалог открыт паролем root — убедитесь, что это осознанно»); пустое поле («консольный root-шелл без аутентификации»); `/etc/shadow` нечитаем («проверка невозможна») |
| `rescue_sulogin_force` | переменная не найдена | `SYSTEMD_SULOGIN_FORCE=1` в override'ах `rescue.service`/`emergency.service` (`/etc/systemd/system/*.d/`), `/etc/default/*`, `/etc/sysconfig/*` |
| `rescue_boot_password` | `superusers` + `password_pbkdf2` найдены в `/boot/grub/grub.cfg` или `/etc/grub.d/` + `user.cfg` | пароль не найден («правка cmdline (`init=/bin/bash`) не защищена») |
| `rescue_grub_user_cfg_perms` | `user.cfg` отсутствует или mode ≤ 0600/root | файл читается не-root («PBKDF2-хеш пароля GRUB доступен для офлайн-перебора») |

Принцип «не смогли проверить ≠ проверка пройдена»: любой сбой чтения
(EACCES, ENOENT там, где файл обязателен) — отдельный WARN с причиной,
никогда не молчаливый INFO. `tessera check` под непривилегированным
пользователем честно сообщает, какие проверки требуют root.

Проверки читают только файлы, ничего не исполняют (никаких `systemctl`,
`grub-mkconfig`): пайплайн работает и в degraded-окружении, поведение
детерминировано для юнит-тестов (пути параметризуются как в
`pam_stack.rs` — корень ФС инъецируется).

### D3. Детект rescue-загрузок — journal предыдущих загрузок + курсор

Monitord при старте (после startup-checks, вне auth-пути):

1. Читает курсор `/var/lib/tessera/rescue_audit_cursor` (последний
   обработанный `boot_id`; отсутствие = первый запуск, обрабатываем
   все доступные загрузки).
2. Перечисляет завершённые загрузки (`journalctl --list-boots -o json`)
   новее курсора.
3. Для каждой ищет факт достижения `rescue.target`/`emergency.target`
   (сообщения systemd unit'ов `rescue.service`/`emergency.service` или
   `JOB_RESULT=done` по target'ам).
4. На каждую находку эмитит audit-событие; переписывает курсор атомарно
   (tmp+rename, как остальные persist'ы).

Событие: target `rescue.audit` (по образцу `mac.audit`/`role.audit`),
имя `rescue_boot_detected`, поля: `boot_id`, `unit`
(`rescue.target`|`emergency.target`), `first_seen_ts` (из journal).
Имя target и события — стабильный API для журнальных grep'ов.

Реализация — `journalctl` как child-процесс (JSON-вывод), не libsystemd
FFI: одноразовый вызов на старте, вне горячего пути; FFI-зависимость
ради этого не окупается. Таймаут и любой сбой journalctl → WARN-лог,
демон продолжает старт (advisory, как D1).

Ограничение: journal должен быть persistent (`/var/log/journal`).
При volatile-журнале предыдущие загрузки невидимы — monitord эмитит
однократный WARN `rescue_audit_blind` (журнал не хранит прошлые загрузки,
аудит rescue-загрузок не работает). Требование включить persistent
journal — в доках рекомендуемой конфигурации.

Альтернатива (свой unit-маркер в rescue.target, файл-флаг) отвергнута:
требует установки наших артефактов в rescue-окружение — расширяем
поверхность канала, который договорились не трогать; и флаг сносится
тем же, кто вошёл.

### D4. Документация: одна каноническая процедура, две лестницы

`docs/ru/operations.md`, раздел «Rescue-канал и восстановление»:

- Рекомендуемая конфигурация: root заблокирован (`*`), `SULOGIN_FORCE`
  отсутствует, пароль GRUB установлен, `user.cfg` 0600, persistent journal.
  Явно: recovery-пункт GRUB `--unrestricted` — приемлемо, потому что
  приводит в закрытый `sulogin`; дверь — пароль на правку cmdline.
- Процедура восстановления — нумерованные лестницы:
  1. система грузится → `sudo` от инженерной УЗ;
  2. система грузится, вход сломан → пароль GRUB, правка строки ядра:
     `init=/bin/bash` (**не** `systemd.unit=rescue.target` — при
     заблокированном root это тупик), `mount -o remount,rw /`, починка,
     `exec /sbin/init` или reboot;
  3. система не грузится → внешний носитель, при FDE — recovery-ключ LUKS,
     chroot.
- Требование: до перевода устройства в cert-only зафиксировать
  местоположение пароля GRUB и recovery-ключа LUKS (сейф/менеджер
  секретов) и проверить процедуру на одном устройстве партии.
- Поведение в emergency: устройство останавливается закрытым (fail-closed),
  диагноз — лестницы 2/3; профилактика ложных emergency — `nofail`
  на некритичных точках монтирования.

`troubleshooting.md` (правка существующего рецепта): текущий текст
рекомендует `systemd.unit=rescue.target init=/bin/bash` — при
заблокированном root первая половина не работает; заменить на
однозначный `init=/bin/bash`-путь.

Threat-model: T8 → mitigations дополняются (проверки, аудит, требование
процедуры); новый design-инвариант: «канал восстановления НЕ ДОЛЖЕН
(MUST NOT) требовать работоспособности Tessera (PAM-модуль, демон, токен,
pcscd)»; формулировка для сертификационных обсуждений: требование
аутентификации в однопользовательском режиме выполняется отказом
(доступ не предоставляется никому).

### D5. Границы capability

- Проверки → delta к `cli-diagnostics` (расширение существующего
  пайплайна, требования к семантике «unable ≠ pass»).
- Аудит загрузок → новая capability `rescue-boot-audit` (детект + событие
  + курсор + degraded-режим volatile journal).
- Доки и threat-model — задачи implement-фазы, не спеки (прецедент
  прошлых changes).

## Risks / Trade-offs

- [Ложные срабатывания `rescue_boot_password` на нестандартных GRUB-схемах
  (не-Astra, chainload, UEFI-only без grub.cfg в ожидаемом пути)] →
  проверка ищет по фиксированному набору путей и честно репортит
  «конфигурация GRUB не найдена» отдельным WARN-текстом, не утверждая
  «пароля нет»; пути покрыты юнит-тестами.
- [journalctl -o json на больших журналах медленный] → вызов один раз
  на старте с `--list-boots` (дёшево) и точечными запросами только
  по новым загрузкам; жёсткий таймаут, сбой = WARN, не блокирует старт.
- [Оператор прочитает INFO `rescue_root_locked` как «канал закрыт»,
  забыв про GRUB] → формулировки записей связные: INFO по root-locked
  ссылается на состояние `rescue_boot_password` («канал закрыт в
  совокупности с паролем загрузчика»).
- [Повторная эмиссия событий при потере курсора (переустановка,
  чистка /var/lib/tessera)] → допустимо: дубль события аудита безопаснее
  пропуска; поля `boot_id` позволяют дедупликацию потребителем.
- [Детект по journal обходится: вошедший в rescue может почистить журнал] →
  осознанное ограничение tamper-evidence-уровня; фиксируется в
  threat-model (сокрытие следов требует отдельного действия, которое
  само оставляет след — усечение журнала); не претендуем на tamper-proof.
- [Разъезд RU/EN доков] → EN-синк в tasks как отдельная задача
  с чек-листом файлов (конвенция bilingual-доков).

## Open Questions

- Нужен ли явный конфиг-флаг отключения rescue-аудита для окружений,
  где journal чистится политикой (сейчас: нет, advisory-поведение
  не мешает)? Решение по первому фидбеку эксплуатации.
- Поведение `sulogin` при `root:*` подтверждено анализом бинаря
  (строка «root account is locked»), но не прогоном на консоли VM —
  прогнать при имплементации доков (лестница 2) и снять точные
  формулировки экрана для troubleshooting.
