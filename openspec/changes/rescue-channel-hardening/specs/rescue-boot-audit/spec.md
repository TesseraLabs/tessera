# rescue-boot-audit Specification

## Purpose

Tamper-evidence rescue-канала: rescue/emergency-загрузка устройства
становится событием аудита при следующем штатном старте monitord.
Физическое обслуживание (легитимное или нет) нельзя предотвратить
средствами ОС — но оно НЕ ДОЛЖНО (MUST NOT) оставаться бесследным.

## ADDED Requirements

### Requirement: Детект rescue-загрузок при старте демона

Monitord при старте ДОЛЖЕН (MUST) определить, достигался ли
`rescue.target` или `emergency.target` в загрузках, завершившихся после
последнего обработанного состояния. Источник — journal предыдущих загрузок;
позиция хранится в курсоре `/var/lib/tessera/rescue_audit_cursor`
(последний обработанный `boot_id`), запись курсора атомарна (tmp+rename).
При отсутствии курсора (первый запуск) обрабатываются все доступные
в journal загрузки.

Детект выполняется один раз на старте, вне auth-пути.

#### Scenario: Устройство загружалось в rescue между стартами
- **WHEN** между предыдущим и текущим стартом monitord устройство
  загружалось с достижением `rescue.target`
- **THEN** при текущем старте monitord эмитит событие аудита
  по этой загрузке и продвигает курсор

#### Scenario: Штатные загрузки без rescue
- **WHEN** все загрузки новее курсора не достигали
  `rescue.target`/`emergency.target`
- **THEN** события не эмитятся, курсор продвигается до последней
  завершённой загрузки

#### Scenario: Потерянный курсор
- **WHEN** файл курсора удалён (переустановка, чистка `/var/lib/tessera`)
- **THEN** monitord заново обрабатывает доступные в journal загрузки;
  возможные повторные события допустимы (дедупликация потребителем
  по `boot_id`), пропуск — нет

### Requirement: Событие аудита rescue_boot_detected

Событие ДОЛЖНО (MUST) эмититься в стабильный tracing-target `rescue.audit`
с именем `rescue_boot_detected` и структурными полями: `boot_id`
(идентификатор загрузки из journal), `unit`
(`rescue.target` | `emergency.target`), `first_seen_ts` (время достижения
target по journal). Имена target, события и полей — стабильный API
для журнальных grep'ов операторов.

#### Scenario: Стабильность имён
- **WHEN** оператор или SIEM-конвейер фильтрует журнал по target
  `rescue.audit` и имени `rescue_boot_detected`
- **THEN** имена неизменны как часть API и продолжают совпадать

### Requirement: Отказы детекта не блокируют старт

Любой сбой детекта ДОЛЖЕН (MUST) логироваться как WARN и НЕ ДОЛЖЕН
(MUST NOT) препятствовать старту демона или влиять на аутентификацию
(недоступный или повреждённый journal, таймаут чтения, нечитаемый курсор).

#### Scenario: Сбой чтения journal
- **WHEN** чтение журнала предыдущих загрузок завершилось ошибкой
  или превысило таймаут
- **THEN** monitord логирует WARN с причиной и продолжает штатный старт;
  курсор не продвигается (загрузки будут обработаны при следующем старте)

### Requirement: Диагностика слепого аудита при volatile journal

При volatile journal monitord ДОЛЖЕН (MUST) однократно за запуск эмитить
WARN `rescue_audit_blind` (нет persistent-хранилища `/var/log/journal`,
предыдущие загрузки невидимы): аудит rescue-загрузок не работает,
требуется persistent journal (см. рекомендуемую конфигурацию в docs).

#### Scenario: Volatile journal
- **WHEN** monitord стартует на системе, где journal не хранит
  предыдущие загрузки
- **THEN** эмитится единственный WARN `rescue_audit_blind`;
  события `rescue_boot_detected` не эмитятся; старт продолжается
