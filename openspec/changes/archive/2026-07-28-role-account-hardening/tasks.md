# Tasks: role-account-hardening

Решение принято: проверка по uid на входе (рубеж 1) + отказ грузить срез с
именем системной учётной записи (рубеж 2). Статический список зарезервированных
имён отвергнут: опасно не имя, а существующая в системе учётная запись с чужими
привилегиями; список расходился бы с дистрибутивом и отвергал законные роли.

- [x] 1. Вход: отказ, если учётная запись из `PAM_USER` системная (uid ниже границы обычных пользователей). Модуль уже делает `getpwnam` на этом пути (`flow.rs:1405`, резолв домашнего каталога) — новой зависимости не нужно
- [x] 2. Загрузка хранилища: срез с именем системной УЗ отвергается с внятной диагностикой; то же в `tessera-cli role lint`
- [x] 3. Границу «системная УЗ» задать одним местом с объяснением, откуда взято значение (1000 — `UID_MIN` в Debian/Ubuntu/Astra); не рассыпать константу по коду
- [x] 4. Тесты: вход в `root` отвергается даже при наличии среза и покрытии удостоверением; ролевая УЗ с uid из обычного диапазона проходит; срез `root.toml` не грузится
- [x] 5. Проверить, что отказ не даёт оракула: имя системной УЗ и её uid и так публичны через `getent`, но диагностика не должна сообщать о наличии/отсутствии среза
- [x] 6. `docs/{ru,en}/install.md`: закрыть остальные пути входа в ролевую УЗ явными командами (`passwd -l`, отсутствие `authorized_keys`, `AuthenticationMethods`, ограничение `su`). Census уже делает `passwd -l` при заведении — сверить и не противоречить
- [x] 7. `docs/{ru,en}/configuration.md`: гарантия «вход закрыт всеми путями» либо подпирается, либо снимается
- [x] 11. Источников класса УЗ два: локальный `/etc/passwd` обязателен (нечитаем → отказ), NSS добавочный (может только добавить отказ, недоступность решения не меняет). Иначе `DynamicUser=`-записи, которых в файле нет, обходят верхнюю границу
- [x] 12. `entry.rs`: `AccountsUnavailable` при загрузке хранилища перестаёт сводиться к `not_found`/`PAM_AUTH_ERR` — своя причина и `PAM_PERM_DENIED`. Загрузка идёт раньше проверки на входе, поэтому именно она решает исход при нечитаемой базе
- [x] 13. `role lint` сверяет имена с локальной базой только по явному объявлению «запуск на целевом устройстве»; совпадение семейства ОС таким объявлением не является
- [x] 14. Одна граница uid в коде, спеке, доках и приёмочных командах: 1000..=61183. `UID_MAX` (60000) — рекомендация провижинингу, не граница отказа
- [x] 15. Предел времени на добавочную проверку: `[roles].account_lookup_timeout_seconds`, дефолт 10, диапазон 1–60, ноль отвергается. Исчерпание = молчание источника (вход по локальному файлу), после первого таймаута резолвер до конца процесса не спрашивается
- [x] 16. Разрешение имён вынести из процесса (fork+exec `getent`, убийство по таймауту): брошенный поток переживал бы выгрузку `pam_tessera.so` и ронял процесс, который аутентифицирует
- [x] 17. Документированные команды линта на устройстве дополнить `--on-device` (`terminal-deployment.md` RU/EN + чек-лист): без флага сверка имён молча пропускается, а команда завершается успехом
- [x] 18. `--on-device` берёт предел времени из конфигурации устройства, а не из зашитого дефолта: иначе линт и вход отвечают по-разному
- [x] 19. Локальную базу читать однократно на загрузку хранилища, а не заново на каждый срез
- [x] 20. Найденный попутно дефект (отдельным коммитом, к этому change'у не относится): клиент OCSP не переживает сигнал — `EINTR` при чтении трактуется как транспортная ошибка. Модуль живёт в чужом процессе, где сигналы штатны, а при fail-closed-отзыве это отказ во входе по причине, не связанной ни с сертификатом, ни с респондером. Повтор обязан укладываться в тот же дедлайн
