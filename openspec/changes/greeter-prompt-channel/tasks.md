# Tasks: greeter-prompt-channel

Кейс раньше кода: каждый пункт с правкой поведения начинается с красного кейса.

## 1. Кейсы на канал показа

- [ ] 1.1 Кейс: диктовка приходит в тексте промпта, а не отдельным сообщением — проверяется
  по тексту промпта, которым запрашивается код (`--answers-per-prompt` уже умеет разбирать
  промпты). Красный до правки `codes_flow`.
- [ ] 1.2 Кейс на класс «первый промпт с эхом невидим»: попытка, где первый промпт с эхом
  отвечен не человеком, а обвязкой, НЕ должна дать успешный вход с подставленным `operator_id`.
  Кейс обязан краснеть на текущем коде — иначе он ничего не сторожит.
- [ ] 1.3 Проверить, что оба кейса гоняются на хосте, а не только на живой Astra: класс
  воспроизводится обвязкой, живое железо для него не нужно.

## 2. Правка потока

- [ ] 2.1 Перенести диктовку из `show_info` в текст промпта кода (`codes_flow.rs`). `show_info`
  остаётся для необязательных пояснений (например, «Код не принят»), от которых вход не зависит.
- [ ] 2.2 Развести порядок промптов так, чтобы `operator_id` не приходил первым промптом с эхом.
  Варианты и их цена — в design.md; решение принять там, а не по месту.
- [ ] 2.3 Проверить длину: строка диктовки плюс приглашение должны читаться на панели греетера
  (перенос темой проверен на ~95 символах, запас невелик).
- [ ] 2.4 Убедиться, что при отказе метод по-прежнему отдаёт коды, описанные в
  `qr-login-method`, — перенос текста не меняет ни одного вердикта.

## 3. Выбор метода входа

- [ ] 3.1 Кейс на каскад: устройство без токена проходит сертификатную строку с
  `PAM_AUTHINFO_UNAVAIL` и попадает на строку `method=code`; неверный PIN каскад НЕ открывает.
- [ ] 3.2 Задокументировать каскадный стек в дистрибутивной документации — сегодня его нет
  нигде, а собирается он без единой строки кода.
- [ ] 3.3 Решить и записать, нужен ли выбор человеком (промпт «удостоверение или код») сверх
  каскада; если да — кейс на то, что выбор виден и на TTY, и на графическом входе.
