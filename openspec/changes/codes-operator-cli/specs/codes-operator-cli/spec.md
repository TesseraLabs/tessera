# codes-operator-cli — консольная выдача кодов

> **Переработано 2026-08-19 под D20–D32** (`tessera-ws` change `codes-phone-channel`).
> Человека-оператора в продукте больше нет: выдачу делает сервер, право выпуска
> оформляется билетом СЕРВЕРА, факт выдачи — грантом с вложенной подписью инженера.
> Консольная выдача сохраняется как открытый инструмент паритета CLI ↔ серверное ядро,
> средство e2e-прогонов и путь для парков без развёрнутого сервера; продуктовым путём
> выдачи она НЕ является (`tessera-ws/specs/commercial-split.md`). Счётчик challenge и
> квитанции упразднены вместе с телефонным каналом.

## ADDED Requirements

### Requirement: Консольная выдача кода
CLI ДОЛЖЕН (MUST) предоставлять выдачу по предъявленному challenge: проверка подписи
challenge ключом устройства из его записи, проверка контрольного символа номера до
вычисления, проверка покрытия запроса рамками билета сервера, проверка совпадения
личного номера инженера в challenge с аутентифицированным инженером, вывод общего ключа
на эфемерной точке из challenge, вычисление кода и его печать. Все проверки ДОЛЖНЫ (MUST)
выполняться тем же ядром и контрактным крейтом, что и серверная выдача; CLI НЕ ДОЛЖЕН
(MUST NOT) содержать собственной реализации формулы, сериализации или проверок, и
расхождений в отказах между CLI и сервером существовать НЕ ДОЛЖНО (MUST NOT).

#### Scenario: Одинаковый отказ в CLI и на сервере
- **WHEN** один и тот же запрос вне рамок билета подан через CLI и через серверное ядро
- **THEN** оба пути отвергают его одной и той же проверкой ядра с эквивалентным объяснением

#### Scenario: Опечатка в номере
- **WHEN** номер устройства введён с ошибкой набора
- **THEN** CLI отклоняет ввод по контрольному символу до вычисления кода

#### Scenario: Challenge без валидной подписи устройства
- **WHEN** предъявлен challenge, чья подпись не сходится с ключом устройства из записи
- **THEN** выдача отклоняется до вычислений: попытка не подтверждена живым устройством

### Requirement: Основание обязательно и в консоли
Выдача через CLI без заполненного основания ДОЛЖНА (MUST) быть невозможна. Основание —
обязательный свободный текст плюс опциональная структурированная ссылка «тип +
идентификатор»; параметр парка ДОЛЖЕН (MUST) допускать требование обязательной ссылки.
Пустая или пробельная строка основанием НЕ ЯВЛЯЕТСЯ (MUST NOT). Основание входит в
подписанный запрос инженера, а не приписывается выдающей стороной отдельно.

#### Scenario: Выдача без основания
- **WHEN** команда выдачи вызвана без основания
- **THEN** команда завершается ошибкой, код не вычисляется и грант не создаётся

### Requirement: Один nonce — один запрос и один грант
CLI ДОЛЖЕН (MUST) отклонять повторную выдачу по challenge-nonce, для которого грант уже
выпущен, и НЕ ДОЛЖЕН (MUST NOT) принимать более одного подписанного запроса на один
nonce. **Проверка счётчика challenge упразднена (MUST NOT):** счётчика не существует —
nonce длинный случайный, состояние попытки живёт в памяти устройства, и запас кода «на
будущее» невозможен по построению.

#### Scenario: Повторная выдача по тому же nonce
- **WHEN** для nonce, по которому грант уже выпущен, подан второй запрос
- **THEN** выдача отклоняется; два гранта на один nonce — тревога сверки, а не рабочий режим

### Requirement: Машиночитаемое различение исходов
CLI ДОЛЖЕН (MUST) различать три исхода кодом возврата: код выдан, продукт ответил отказом,
инструмент до ответа не дошёл (файл не читается, ключ недоступен, токен молчит). Последний
класс НЕ ДОЛЖЕН (MUST NOT) быть неотличим от отказа. При отказе ДОЛЖЕН (MUST) печататься
стабильный машиночитаемый класс отказа, НЕ подлежащий локализации; отказы по рамкам билета
ДОЛЖНЫ (MUST) быть узнаваемы как группа. Локализованный текст остаётся для человека и
опорой автоматики быть НЕ ДОЛЖЕН (MUST NOT). Значения кодов и имена классов ДОЛЖНЫ (MUST)
быть закреплены тестом, а не только документацией.

Границу между вердиктом и сбоем ДОЛЖНО (MUST) проводить так: документ, не прошедший
проверку, — это вердикт; документ, который вообще не является документом, — сбой
окружения. Просроченный или подделанный билет — вердикт; обрезанный файл билета — сбой.
Challenge — исключение в пользу вердикта: он приходит от инженера, а не из окружения,
поэтому неразобравшийся challenge (в том числе битый контрольный символ номера или
несошедшаяся подпись устройства) — отказ, а не сбой.

#### Scenario: Стенд отличает вердикт от сбоя
- **WHEN** выдача отказала по рамкам билета, а в другом прогоне не нашла файл ключа
- **THEN** коды возврата различаются, и автоматика не принимает сбой окружения за
  проверенную гарантию

#### Scenario: Перевод сообщений не ломает автоматику
- **WHEN** формулировка отказа переведена или переписана
- **THEN** класс отказа и код возврата не меняются

### Requirement: Источник публичного ключа устройства без реестра
CLI ДОЛЖЕН (MUST) принимать запись устройства файлом, без какого-либо реестра и точки
обмена: проверяются PoP-подпись ключом устройства, подпись организации, её цепочка до
корня парка и подпись владельца по digest всей записи. Отсутствие реестра НЕ ДОЛЖНО
(MUST NOT) быть условием работы консольной выдачи.

#### Scenario: Обслуживание парка без реестра
- **WHEN** у владельца небольшого парка нет ни точки обмена, ни сервера, а запись
  устройства лежит файлом
- **THEN** выдача кода выполняется после проверки всех трёх подписей записи

### Requirement: История выдач ведётся так, чтобы её нельзя было тихо переписать
История выдач ДОЛЖНА (MUST) вестись в хеш-цепочечном реестре, запись в него ОБЯЗАТЕЛЬНА и
выполняется ДО печати кода. Порванная цепочка ДОЛЖНА (MUST) читаться как сбой окружения, а
не как «истории нет». Голова цепочки ДОЛЖНА (MUST) заверяться внешне — ключом домена
владельца, отдельным от ключа выдачи, с сохранением у заверителя `{идентификатор журнала,
последний seq, последняя голова}` и запретом двух подписей на один seq; иначе откат к
раннему seq и построение другой ветки остаются незаметными.

Границы механизма ДОЛЖНЫ (MUST) быть записаны честно: правка или изъятие строки из
середины предотвращены цепочкой; обрезание незаверенного хвоста цепочкой НЕ ловится;
полное уничтожение истории на машине владельца не предотвратимо в принципе. Последний
рубеж — сверка трёх артефактов: подпись запроса инженера ↔ грант ↔ журнал устройства,
стык по nonce.

#### Scenario: Реестр правлен
- **WHEN** строка в середине реестра изменена или удалена
- **THEN** цепочка не сходится, и это сбой окружения, а не пустая история

#### Scenario: Форк истории после отката
- **WHEN** история откачена к раннему seq и продолжена другой веткой
- **THEN** внешний заверитель отказывает: сохранённая у него голова не является предком
  предъявленной

### Requirement: Грант и сверка в консоли
CLI ДОЛЖЕН (MUST) выпускать грант каждой выдачи в том же формате, что серверное ядро
(подписанный запрос инженера внутри, подпись выдающей стороны снаружи, при уровне от
порога четырёх глаз — подпись подтверждающего), и предоставлять проверку гранта, показ
рамок и происхождения билета, а также сверку трёх артефактов с вывезенными журналами
устройств (вход без парного запроса, запрос без парного входа, дубли на один nonce).
Отчёт сверки без стороны устройств ДОЛЖЕН (MUST) помечаться неполным. **Формат квитанции
оператора удалён (MUST NOT):** его место занял грант.

#### Scenario: Сверка без сервера
- **WHEN** владелец сверяет гранты и вывезенные журналы устройств консольной командой
- **THEN** получает те же классы тревог, что дало бы серверное ядро, либо явную пометку
  неполноты, если сторона устройств отсутствует

### Requirement: Ключ выдающей стороны на токене
Приватный ключ выдающей стороны ДОЛЖЕН (MUST) браться с PKCS#11-токена или из аппаратного
модуля; адресация — по `CKA_ID`. Софт-хранилище ключа допустимо ТОЛЬКО как явно включённый
режим, и способ хранения ДОЛЖЕН (MUST) отмечаться в гранте — иначе постфактум невозможно
отличить выдачу, защищённую аппаратно, от выдачи ключом с диска.

Компрометация этого ключа ДОЛЖНА (MUST) рассматриваться как способность выпускать коды в
рамках билета до его отзыва; обнаружение — сверкой («вход без парного подписанного
запроса»), а не локальным отказом устройства.

#### Scenario: Выдача софт-ключом
- **WHEN** выдающая сторона работает в явно включённом режиме софт-хранилища
- **THEN** выдача выполняется, и грант несёт отметку способа хранения ключа
