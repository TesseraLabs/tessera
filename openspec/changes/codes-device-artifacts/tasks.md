## 1. Формат пакета

- [x] 1.1 `role::ManifestCodes` в подписанном манифесте и тот же вид в `codes.toml` standalone-пакета;
      чтение и сверка пинов — `enrollment::codes`, проводка — `EnrollmentPackage::install_with_codes`,
      командная строка — `tessera enroll --codes-pin-file|--codes-dir|--no-codes`
- [x] 1.2 Билеты, список отзыва и якорь разбираются `codes::tickets` (`TicketStore::parse`,
      `TicketAnchor::parse`), которые зовут `tessera_codes_contract`; своего парсера нет
- [x] 1.3 Обратная совместимость проверена прогоном на трёх уровнях: `enrollment::codes::tests`
      (managed и standalone пакеты без части Codes), `tessera_cli::enroll::tests`
      (`a_package_without_a_codes_part_imports_as_before` — импорт проходит, хранилище пусто)
- [x] 1.4 Секция Codes приходит ровно из тех байтов, на которых сошлась подпись:
      манифест читается ОДИН раз, подпись проверяется до любого решения по его
      содержимому (включая путь повторного `bundle_version`, где Access-части делать
      нечего), секция передаётся значением. До этого `codes_section()` перечитывал
      манифест с носителя после установки — подменённый в окне носитель отдавал чужой
      якорь доверия билетов. Хуже того: на пути повторного `bundle_version` подпись не
      проверялась ВООБЩЕ — Access-части делать нечего, ранний выход стоял до проверки, и
      подмена не требовала даже гонки во времени. Стережёт
      `a_codes_section_reaches_the_store_only_under_a_signature_that_held`; проверено, что
      без правки он красный
- [x] 1.5 Требование записано в спеку change'а («Подпись манифеста проверяется до любого
      решения по его содержимому», `specs/device-enrollment/spec.md`) — с обоими сценариями:
      повторная подача пакета с применённым номером версии и переписанный между проверкой и
      применением носитель. Без этой строки ранний выход по версии вернётся при следующей
      правке импорта. `openspec validate codes-device-artifacts --strict` — valid

## 2. Носитель

> Раздел не делался осознанно: чтение пакета с CCID-токена и партионная адресация
> требуют живого носителя, которого не объявляет ни один e2e-профиль, и едут
> отдельной задачей волны. Кейсы на них в реестр не заводились — заготовка с
> невыполнимым `requires` даёт `SKIP`, а не проверку.

- [ ] 2.1 Чтение пакета из PKCS#11 data-объектов (публичные и приватные под PIN)
- [ ] 2.2 Сборка объекта из чанков с проверкой хеша; отсутствие или расхождение чанка — отказ импорта целиком
- [ ] 2.3 Партионное оглавление: адресное чтение своего per-device контейнера по номеру устройства
- [ ] 2.4 Тесты: чужие контейнеры на носителе не мешают; своего контейнера нет — внятный отказ без частичного применения
- [ ] 2.5 Строгий fail-closed разбор новой поверхности (структура, подписи) — негативные тесты на каждый класс порчи

## 3. Эпохи ключа

- [x] 3.1 `codes::epoch` (файл `state/key.epoch`, root-only, atomic) + сброс `nonce.counter`
      и `nonce.state` при большей эпохе — `codes::artefacts::apply`
- [x] 3.2 Anti-rollback: меньшая эпоха отвергается, ключ, счётчик и эпоха не меняются
- [x] 3.3 Повтор той же эпохи — no-op без сброса счётчика; ключ переписывается только
      если хранилище его потеряло
- [x] 3.4 Прогнано: `the_same_epoch_again_does_not_resurrect_consumed_nonces` (счётчик 31 → 31),
      `a_greater_epoch_replaces_the_key_and_retires_the_nonces` (42 → 0, ключ заменён),
      `a_smaller_epoch_is_refused_and_changes_nothing`, `a_repeated_epoch_restores_a_key_the_store_has_lost`
- [x] 3.5 Эпоха, под которой считается код, берётся из хранилища, а не из конфигурации
      (`epoch::effective` + `CodeMethod::open_inner`): импорт новой эпохи не правит `config.toml`,
      и без этого устройство считало бы коды со старым номером при новом ключе. Конфигурация
      впереди хранилища — отказ с обоими числами, а не тихий расчёт. Наблюдаемую сторону
      стережёт `a_key_delivered_under_a_new_epoch_is_the_one_the_login_computes_with`:
      импорт кладёт новую пару под эпохой N+1, устройство обязано объявить в challenge N+1 и
      принять код, посчитанный оператором по ключу этой эпохи. Проверено, что без правки он
      красный (падает на объявленной эпохе)

## 4. Un-enroll

      `nonce.counter`, `nonce.state`, `key.epoch`
- [x] 4.2 Последняя эпоха читается ДО удаления и уходит в `codes_artefacts_wiped`
- [x] 4.3 Устройство без артефактов вытирается штатно и сообщает пустой результат

## 5. Ротация билетов

- [x] 5.1 Ротация едет той же секцией пакета без контейнера ключа (`a_rotation_carries_tickets_without_a_key`);
      применение до аутентификации даёт `CodeMethod::open`, читающий билеты и список отзыва на каждой попытке
- [x] 5.2 Монотонность правилом надмножества: набор, потерявший номер, отвергается
      (`a_revocation_list_that_forgot_a_number_is_refused`, `a_revocation_list_that_only_grows_is_accepted`)
- [x] 5.3 Отзыв закрывает вход в ближайшей же попытке: список читается при каждом открытии
      метода, прогнано `a_revoked_ticket_closes_the_method_for_that_operator` и
      `a_revocation_that_arrives_between_two_logins_takes_effect`. Снаружи то же стережёт
      ENRC-006 (отзыв привезён пакетом), красный до появления кода в main

## 6. Приёмка

- [x] 6.1 E2E-кейсы в `tests/e2e/cases/28-codes-enrollment.yaml` (ENRC-001…007) + хелпер
      `tests/e2e/helpers/codes-enroll.sh`: импорт пакета с частью Codes, пакет без неё,
      смена эпохи со сбросом счётчика, реплей старой эпохи, повтор той же эпохи,
      отзыв билета пакетом, un-enroll с вытиранием. Кейсы красные и записаны в
      `BASELINE.md` с причинами. Импорта с CCID-токена и партионного носителя среди них
      нет — см. врезку к разделу 2
- [x] 6.2 `cargo clippy --all-targets` по `tessera_core`, `pam_tessera`, `tessera_cli` чист в
      обоих наборах фич (`--all-features` и дефолтный) — по нулю замечаний в каждом из шести
      прогонов. `tessera_issuer` и `xtask` в матрицу не входят: там незавершённый переход
      журнала на `tessera_hashchain`, чужая зона
- [ ] 6.3 Pre-merge gate: `threat-model` + `vuln-scan` для новой поверхности разбора носителя

## 7. Побочные обязательства волны

- [x] 7.1 `[codes].key_password` убран: ключ в хранилище лежит без пароля, PIN остался формой
      доставки и подаётся `tessera enroll --codes-pin-file`. Ключ конфигурации не просто удалён,
      а отвергается по имени (`RemovedKey` + объясняющее сообщение), чтобы обновляющий парк
      оператор отличил осознанное изменение от опечатки
- [x] 7.2 Секция `[codes]` описана в `dist/config/config.toml.example` — с явной пометкой, что
      артефакты не конфигурируются, а доставляются, и почему пароля контейнера там больше нет
- [ ] 7.3 `helpers/codes-phone.sh` кладёт в хранилище PIN-закрытый `device.p12` и после 7.1 будет
      красным на материале ключа. Чинится либо продуктовым импортом в этом хелпере, либо хранимой
      формой контейнера в `cargo xtask codes-fixtures` — генератор сейчас не собирается (см. 6.2),
      поэтому записано в `BASELINE.md` и помечено в самом хелпере
- [x] 7.4 Находки ревью в моём периметре закрыты, каждая с тестом, краснеющим без правки:
      **H5** — `resolve_codes` не глотает ошибку чтения конфигурации (`EnrollError::ConfigUnreadable`
      до начала импорта; исключение — явный `--codes-dir`), иначе артефакты уезжали в дефолтное
      хранилище, а доставленный контейнер затирался с носителя;
      **профили** — `[codes].profile`, который устройство не умеет (`x25519`, ГОСТ), отвергается
      при загрузке, а не отказом на каждом коде у клавиатуры; источник истины один —
      `codes::agreement::device_supports` рядом с `curve_of`, которую использует само согласование;
      **M4** — `codes.toml` больше не уезжает в каталог ролей;
      **L1** — пример конфигурации называет только работающие значения (`crockford-base32`,
      `p256`), а тест `every_codes_value_the_example_names_is_accepted` гоняет каждое названное
      значение через ПОЛНУЮ валидацию и запрещает предлагать неработающее;
      **L2** — чтение PIN через `O_NOFOLLOW|O_CLOEXEC|O_NONBLOCK` с отказом по «не обычный файл»
      и буферами `Zeroizing`. Первая правка L2 дефект НЕ закрыла (проверка типа после открытия —
      открытие FIFO виснет до появления писателя); поймал тест, закрыл `O_NONBLOCK`
- [x] 7.5 Тест `an_unconfirmed_profile_needs_the_fleet_owner_to_accept_it` заменён на
      `accepting_the_vendor_gate_does_not_make_an_unrunnable_profile_load`: прежний закреплял, что
      принятие вендорского гейта делает ГОСТ-конфигурацию загружаемой, — а согласования для неё
      на устройстве нет. Сам гейт не ослаблен, он живёт и проверяется в контрактном крейте
- [x] 7.6 Хранилище Codes известно и при выключенном методе: `CodesSection` несёт `paths` всегда,
      а импорт читает их вместо дефолта. Парк готовят до включения метода, поэтому пакет с ключом
      импортируют при `enabled = false`; прежде ключ уезжал в `/var/lib/tessera/codes`, вход потом
      смотрел в настроенный каталог, а контейнер доставки к этому моменту уже затёрт — единственная
      копия ключа оказывалась не там. Тесты: `a_disabled_section_still_says_where_the_store_is`,
      `the_enabled_section_and_the_store_it_reports_are_the_same_paths` и на уровне команды
      `the_import_writes_into_the_configured_store_even_before_the_method_is_enabled`
      (проверено краснение: без правки даёт `/var/lib/tessera/codes/device.p12`)
- [x] 7.7 Секция `[audit]` описана в примере конфигурации вместе со связкой: включение
      `[codes].enabled` включает и журнал, явный `[audit].enabled` перекрывает связку в обе стороны.
      Текст объясняет ПОЧЕМУ так: контроль над оператором держится на сверке «входы против
      квитанций», и устройство, предлагающее метод без журнала, сломано так, как само обнаружить
      не может. Значения `refuse | rotate` проходят ПОЛНУЮ валидацию на включённой секции (оба
      приняты — находки нет), а сама связка закрыта тестом
      `the_journal_follows_the_code_method_unless_the_section_says_otherwise`: описанное в примере
      поведение без теста разойдётся с кодом на первой же правке
