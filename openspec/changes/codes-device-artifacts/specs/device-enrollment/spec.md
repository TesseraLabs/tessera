# device-enrollment — артефакты Codes в enrollment-пакете

## ADDED Requirements

### Requirement: Опциональная часть Codes в enrollment-пакете
Enrollment-пакет ДОЛЖЕН (MUST) допускать опциональную часть Codes: PIN-контейнер с приватным
ключом устройства, номер эпохи ключа, набор действующих билетов операторов и список отзыва
билетов. Пакет без этой части ДОЛЖЕН (MUST) оставаться валидным — парк «только Access»
готовится тем же процессом. Включение Codes на действующем парке ДОЛЖНО (MUST) выполняться
доставкой недостающих артефактов курьерским payload, без перераскатки устройства и без
повторного enrollment. Разбор артефактов Codes ДОЛЖЕН (MUST) выполняться крейтом контракта;
собственного парсера билетов и записей реестра здесь быть НЕ ДОЛЖНО (MUST NOT).

#### Scenario: Пакет без части Codes
- **WHEN** импортируется enrollment-пакет парка «только Access»
- **THEN** импорт проходит как прежде, устройство становится рабочим, метод входа по коду
  просто недоступен

#### Scenario: Включение Codes на действующем устройстве
- **WHEN** на работающее Access-устройство приезжает payload с контейнером ключа и билетами
- **THEN** артефакты применяются, метод входа по коду становится доступен, перераскатка
  и повторный enrollment не требуются

### Requirement: Хранение ключа устройства после импорта
После импорта приватный ключ устройства ДОЛЖЕН (MUST) храниться в root-only хранилище —
PIN-контейнер является формой доставки ключа, а не формой его хранения на устройстве:
права `0600`, владелец root, каталог `0700`, доступ процессу проверки кода без
участия человека: код проверяется в момент входа, у клавиатуры стоит инженер, который PIN
устройства знать не должен, и вводить его при каждой загрузке банкомата некому.
Спека и документация ДОЛЖНЫ (MUST) фиксировать вытекающее ослабление явно: на устройстве
ключ защищён правами файловой системы и целостностью среды (доверенная загрузка, замкнутая
программная среда), а не PIN — то есть той же границей, за которой у нас уже находится
«root на устройстве» (threat-model §3). Хранение импортированного ключа в мире, доступном
не-root процессам, ЗАПРЕЩЕНО (MUST NOT). Материал ключа НЕ ДОЛЖЕН (MUST NOT) оставаться в
каталоге импорта после переноса в хранилище.

#### Scenario: Устройство перезагрузилось без человека
- **WHEN** банкомат загрузился после отключения питания, и инженер набирает вход по коду
- **THEN** проверка кода работает без ввода каких-либо секретов при загрузке

#### Scenario: Права хранилища ослаблены
- **WHEN** каталог или файл ключа доступны не-root процессу
- **THEN** самопроверка устройства сообщает об этом как о нарушении предпосылки,
  и метод входа по коду не активируется

### Requirement: Чтение пакета с CCID-токена
Импорт ДОЛЖЕН (MUST) поддерживать чтение enrollment-пакета из PKCS#11 data-объектов чистого
CCID-токена наравне с примонтированным носителем: в парках, где USB mass-storage запрещён
политикой, это единственный проходящий путь доставки. Приватная часть пакета ДОЛЖНА (MUST)
читаться приватными data-объектами (под PIN), публичная — публичными. Разбор ДОЛЖЕН (MUST)
быть строгим и fail-closed: неизвестная структура, битая подпись, несобранный из чанков
объект — отказ импорта без частичного применения.

#### Scenario: Парк с запретом mass-storage
- **WHEN** политика устройства запрещает монтирование USB-накопителей
- **THEN** enrollment-пакет импортируется целиком через data-объекты токена, без единого
  монтирования

#### Scenario: Неполный набор чанков на носителе
- **WHEN** объект пакета разрезан на чанки и один из них отсутствует или не сходится по хешу
- **THEN** импорт отвергается целиком, устройство остаётся в прежнем состоянии

### Requirement: Партионная адресация носителя
Импорт ДОЛЖЕН (MUST) поддерживать носитель, несущий пакеты для нескольких устройств: общая
часть парка (билеты, список отзыва, роли, цепочка) читается целиком, а per-device часть —
адресно по номеру устройства через оглавление носителя. Устройство НЕ ДОЛЖНО (MUST NOT)
импортировать чужие per-device контейнеры и НЕ ДОЛЖНО (MUST NOT) требовать их отсутствия
на носителе.

#### Scenario: Рейс по нескольким устройствам
- **WHEN** инженер настраивает устройства партии с одного носителя
- **THEN** каждое устройство импортирует общую часть и только свой контейнер, остальные
  контейнеры на носителе ему не мешают

#### Scenario: Своего контейнера на носителе нет
- **WHEN** номер устройства отсутствует в оглавлении носителя
- **THEN** импорт отвергается с внятной диагностикой, частичного применения общей части
  не происходит

### Requirement: Эпоха ключа и её anti-rollback
Часть Codes ДОЛЖНА (MUST) нести номер эпохи ключа устройства. Импорт пакета с эпохой больше
текущей ДОЛЖЕН (MUST) заменять приватный ключ и сбрасывать счётчик nonce в ноль; коды прежней
эпохи после этого НЕ ДОЛЖНЫ (MUST NOT) верифицироваться. Импорт пакета с эпохой меньше
зафиксированной ДОЛЖЕН (MUST) отвергаться тем же anti-rollback, что и `bundle_version`.
Повторный импорт той же эпохи ДОЛЖЕН (MUST) быть идемпотентным no-op и НЕ ДОЛЖЕН (MUST NOT)
сбрасывать счётчик nonce.

#### Scenario: Смена эпохи после восстановления устройства
- **WHEN** устройство восстановлено из бэкапа и получило пакет с новой эпохой
- **THEN** ключ заменён, счётчик обнулён, записанные ранее коды не принимаются

#### Scenario: Реплей пакета прежней эпохи
- **WHEN** на устройство подан пакет с эпохой меньше текущей
- **THEN** импорт отвергается (anti-rollback), ключ и счётчик не меняются

#### Scenario: Повторный импорт той же эпохи
- **WHEN** тот же пакет импортируется второй раз
- **THEN** операция — no-op; счётчик nonce НЕ сбрасывается (иначе повтор носителя воскресил
  бы уже потреблённые значения)

### Requirement: Ротация билетов курьерским payload
Билеты операторов и список их отзыва ДОЛЖНЫ (MUST) обновляться курьерским payload тем же
ритмом и механикой, что CRL, и ДОЛЖНЫ (MUST) применяться до аутентификации. Список отзыва
ДОЛЖЕН (MUST) быть монотонным: приём набора старее применённого отвергается.

#### Scenario: Отзыв билета доставлен с payload
- **WHEN** инженер привёз payload с обновлённым списком отзыва билетов
- **THEN** список применяется до аутентификации, и коды отозванного оператора отклоняются
  уже в этой попытке входа

### Requirement: Подпись манифеста проверяется до любого решения по его содержимому
Подпись `manifest.toml` ДОЛЖНА (MUST) проверяться прежде, чем импорт примет хотя бы одно
решение по значениям из этого манифеста, — включая решение о том, что работы нет. Ранний
выход по совпадению `bundle_version` ДОЛЖЕН (MUST) находиться ПОСЛЕ проверки подписи, а не
до неё: пакет с уже применённым номером версии не даёт Access-части никакой работы, и
проверка «в составе установки» на этом пути не выполняется вовсе.

Артефакты, названные манифестом, ДОЛЖНЫ (MUST) браться из тех же байтов, на которых сошлась
подпись. Повторное чтение файла с носителя после проверки ЗАПРЕЩЕНО (MUST NOT): пакет живёт
на съёмном носителе, его хозяин вправе переписать содержимое между двумя чтениями, и
подписанными оказываются одни байты, а применёнными — другие. Правило распространяется на
часть Codes наравне с CRL и `.p12`: секция называет удостоверяющий центр билетов, то есть
решает, чьи коды устройство впустит.

#### Scenario: Повторная подача пакета с уже применённым номером версии
- **WHEN** на устройство подан пакет, чей `bundle_version` равен уже применённому, а подпись
  манифеста не сходится
- **THEN** импорт отвергается по подписи; отсутствие работы для Access-части не превращает
  неподписанный пакет в успешный no-op

#### Scenario: Носитель переписан между проверкой подписи и применением
- **WHEN** содержимое манифеста на носителе подменено после того, как его подпись проверена
- **THEN** устройство применяет ровно проверенные байты; подменённая секция `[codes]` не
  попадает в хранилище, и якорь доверия билетов не меняется
