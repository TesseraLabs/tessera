## 1. Тесты вперёд

- [ ] 1.1 Красный тест: `open_session` без `pam_data`, но с валидным ключом в окружении и файлом на месте — контекст восстанавливается
- [ ] 1.2 `pam_data` остаётся первым источником: при наличии контекста в хендле файл не читается вовсе
- [ ] 1.3 Отсутствие ключа в окружении, отсутствие файла, чужой ключ, файл с испорченным содержимым — каждый случай даёт отказ, а не частично восстановленный контекст
- [ ] 1.4 Повторное потребление одного ключа невозможно: второй читатель не получает контекст (захват атомарный)
- [ ] 1.5 Просроченный по TTL файл не принимается
- [ ] 1.6 Контекст, восстановленный из файла, идентичен положенному — включая снапшот роли и потолок целостности, а не только идентичность

## 2. Хранилище

- [ ] 2.1 Отдельный каталог `root:root 0700` (своя строка в `dist/tmpfiles/`), НЕ `/run/tessera` — тот принадлежит непривилегированному `tessera`
- [ ] 2.2 Файлы `0600`, создание `O_EXCL`, чтение через доверенный dirfd с `O_NOFOLLOW`
- [ ] 2.3 Захват атомарный — `rename` перед чтением, не «прочитал и удалил»: последнее не эксклюзивно для двух читателей
- [ ] 2.4 Уборка по TTL только root-механизмом; monitord доступа в этот каталог иметь не должен
- [ ] 2.5 Содержимое файла не переживает логин дольше необходимого; при отказе на любом шаге файл удаляется

## 3. Передача ключа

- [ ] 3.1 Ключ — существующий `session_id`, без второго идентификатора
- [ ] 3.2 Файл пишется ДО публикации ключа в окружении: обратный порядок даёт читателю ключ, за которым ещё ничего нет
- [ ] 3.3 Сбой `pam_putenv` — fail-closed: файл удаляется, логин не продолжается в состоянии, где session-фаза заведомо не найдёт контекст
- [ ] 3.4 Ключ вычищается из PAM-окружения сразу после потребления — иначе идентификатор утечёт в окружение пользовательской сессии
- [ ] 3.5 Восстановленный контекст кладётся в `pam_data` хендла монитора: второй вызов `open_session` и `close_session` берут его оттуда, а не читают файл повторно

## 4. Потребители

- [ ] 4.1 `pam_sm_open_session` — фолбэк на файл при отсутствии `pam_data`
- [ ] 4.2 `pam_sm_close_session` — сегодня мягко пропускает хуки без контекста; после фикса контекст есть, и хуки должны отработать
- [ ] 4.3 Парность реестра monitord: `open_session` регистрируется в auth-форке, а закрывается в мониторе — проверить, что запись больше не висит. Это существующая утечка под sshd, закрывается тем же фиксом
- [ ] 4.4 `acct_mgmt` фолбэк НЕ получает: под sshd он идёт в том же форке, что `authenticate`. Добавлять только если появится вызывающий, гоняющий его в третьем процессе

## 5. Безопасность

- [ ] 5.1 Разобрать поверхность: кто может создать, прочитать, подменить, удалить файл; что даёт TOCTOU между `rename` и чтением
- [ ] 5.2 Сверить с реестром угроз (T4, T11) — записанный контекст определяет MAC-метку, окружение root-хуков и аудитную личность, его подделка обязана требовать root
- [ ] 5.3 Убедиться, что содержимое файла не даёт ничего тому, кто прочитал его без права применить: контекст не заменяет проверку сертификата, а переносит её результат
- [ ] 5.4 Ревью изменений
