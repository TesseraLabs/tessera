# Контекст аутентификации между процессами PAM

## Why

Реальный `ssh serv@host` в режиме `cert-only` не доходит до шелла. Аутентификация
проходит, PIN принимается, печатается баннер — и соединение рвётся:
`pam_open_session(): Authentication service cannot retrieve authentication info`.

Причина в том, что OpenSSH ведёт PAM-диалог из двух разных процессов
(privilege separation). В журнале стенда это видно прямо: `USER_AUTH` и
`USER_ACCT` помечены `pid=6833`, а `USER_START ... res=failed` — `pid=6831`.
`pam_tessera` кладёт `AuthContext` через `pam_set_data`, а это по построению
живёт внутри одного `pam_handle_t` и не переживает границу процесса ничем.
`pam_sm_open_session` не находит контекст и возвращает `PAM_AUTHINFO_UNAVAIL`
(`entry.rs`), что здесь fail-closed по задокументированному решению — просто
это решение не предполагало вызывающего, который расщепляет фазы.

Воркэраунда нет: ни `/etc/pam.d/sshd`, ни `sshd_config`, ни `config.toml` не
управляют тем, в скольких процессах вызывающий ведёт PAM-диалог.

`pamtester` этот класс сбоя не воспроизводит в принципе — он ведёт весь диалог
в одном процессе, поэтому зелёный прогон там ничего не доказывает.

Затронут только sshd. По замеру модели процессов на стенде: `fly-dm` держит один
долгоживущий процесс дисплея на весь uptime, `login`/`agetty` — процесс на tty,
`sudo` однопроцессный. То есть чинить надо один путь, а не архитектуру продукта.

Побочно вскрылось: под sshd уже сейчас копятся незакрытые записи в реестре
monitord. `monitor.open_session` регистрируется внутри `pam_sm_authenticate`, то
есть в auth-форке, а закрыть её некому — `run_open_session_pipeline` до реестра
не доходит (обрыв раньше), cleanup при отказе MAC недостижим, а
`pam_sm_close_session` без контекста мягко пропускает хуки. Это отдельная утечка,
которую тот же фикс закрывает попутно.

## What Changes

`AuthContext` переносится между процессами: auth-фаза пишет его в файл, а
session-фаза читает. Связывает две фазы существующий `session_id`, который
передаётся через **PAM-окружение** — единственный канал, который OpenSSH
переносит из auth-форка в монитор штатно (`pam_getenvlist` у ребёнка →
`import_environments` → `pam_putenv` в хендле монитора). `pam_set_data` не
переносится ничем.

Это снимает открытый вопрос «чем надёжно связать две фазы»: искать совпадающие
PAM-items и строить эвристику не нужно, потому что ключ можно передать явно.
Параллельные логины одним аккаунтом различаются без угадывания. На том же
механизме годами живут `pam_krb5` и sssd, передавая `KRB5CCNAME` под privsep.

`pam_data` остаётся первым источником: однопроцессные вызывающие
(`fly-dm`, `login`, `sudo`, `pamtester`) файла не касаются вовсе.

Хранилище — **отдельный каталог `root:root 0700`**, не `/run/tessera`. Это
поправка к первоначальному предложению «по образцу `MOUNTPOINT_BASE`»:
`/run/tessera` создаётся как `0750 tessera tessera`, потому что демон осознанно
депривилегирован, — а владелец каталога может подменять записи в нём. Записанный
`AuthContext` определяет MAC-метку, окружение root-хуков и аудитную личность,
поэтому его подделка должна требовать root, иначе скомпрометированный monitord
получил бы способ подсунуть root-процессу PAM поддельный контекст.

### Что отвергнуто и почему

**Сделать `acct_mgmt`/`open_session` самодостаточными без `AuthContext`** — это
регресс безопасности, а не фикс. `open_session` требует данных, производных от
сертификата: потолок целостности для MAC-метки (с проверкой превышения),
идентичность для аудита, снапшот роли (инвариант «правка role store не влияет на
живую сессию»), `session_id` для парности с `close_session`. Без сертификата их
не восстановить: USB размонтирован по дизайну, PIN в session-фазе недоступен.
Выводить всё из `PAM_USER` означало бы отказаться от `verified_session_account` —
существующей защиты от подмены `PAM_USER` между фазами. Отдельно: под sshd
`acct_mgmt` и так работает, он идёт в том же форке, что и `authenticate`;
ломаются только `open_session`/`close_session`.

**Уйти от PAM для SSH на `AuthorizedKeysCommand`** — не решает баг: при
`UsePAM yes` `pam_sm_open_session` всё равно вызывается и всё равно без
контекста. Плюс лобовое противоречие канону роль-учёток («заблокированный
пароль, нет `authorized_keys`, единственный путь — cert-аутентификация»). Это
самостоятельный продуктовый разговор про SSH-доступ с настоящими SSH-ключами, а
не починка текущего пути.

## Impact

- `openspec/specs/cert-authentication-flow/spec.md` — требование «Mount живёт
  только в auth-фазе» утверждает, что контекст передаётся в `open_session` через
  `pam_data`. Транспорт расширяется.
- `crates/pam_tessera` — `data_handle.rs` (или новый модуль), `entry.rs`
  (`pam_sm_open_session`, `pam_sm_close_session`), возможно `session.rs`.
- `dist/tmpfiles/` — новая строка под root-каталог.
- Поверхность атаки: новый файл с состоянием аутентификации. Обе стороны — root,
  новой границы привилегий не появляется, но требования к режиму, владельцу,
  атомарности захвата и уборке обязаны быть выполнены целиком, иначе появляется.

## Предпосылка проверена

Замысел держался на одном непроверенном факте — доходит ли PAM-окружение из
auth-форка до монитора. **Проверено на стенде 2026-08-09: доходит.**

Временный PAM-модуль клал переменную в `pam_sm_authenticate` и читал её в
остальных фазах, каждая писала свой pid. Живой `ssh` по keyboard-interactive:

```
ACCT     pid=2575  probe=nonce-2575-1786286541
SESSION  pid=2573  probe=nonce-2575-1786286541
CLOSE    pid=2573  probe=nonce-2575-1786286541
```

Расщепление воспроизведено, значение из auth-форка прочитано монитором.
Сборка стенда — `OpenSSH_9.6p1 Debian-2~deb10u1astra8se13+b2`, Astra 1.8.4.

Попутно подтвердились два наблюдения баг-репорта: `acct_mgmt` идёт в том же
процессе, что `authenticate` (ломаются только session-фазы), а при входе по
publickey PAM auth-фаза не выполняется вовсе и все фазы идут одним процессом —
то есть расщепление специфично для keyboard-interactive, ровно для пути tessera.

Что осталось непроверенным: поведение на другой сборке OpenSSH (вывод получен на
одной), и сколько раз за логин вызывается `open_session` на стеке С интеграцией
tessera — проба шла на стеке без неё.
