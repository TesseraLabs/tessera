## 5. Служба

- [x] 5.1 Крейт `tessera_win_service`: SCM-интеграция (`install`/`uninstall`/`start`/`stop`, `StartServiceCtrlDispatcherW`, LocalSystem, panic-guard на обеих точках обратного вызова), команда `run` для стенда, логирование через `tracing`. Не сделано осознанно: recovery-политика SCM (автоперезапуск) — волна 2
- [x] 5.2 Сборка зависимостей для службы: `di::wire_with_monitor` принимает клиента монитора от вызывающего и собирает всё остальное (включая подбор `[[trust_override]]`); `di::wire` остался Unix-обёрткой, открывающей AF_UNIX-сокет, — сигнатура для `entry.rs` не изменилась. Модуль `di` доступен на Windows целиком; заглушки монитора внутри `wire` нет
- [x] 5.3 Класс учётной записи на Windows: `role::windows_account` — правила поверх well-known SID и RID локальной УЗ, `SystemAccounts::device` на Windows строится на нём вместо `/etc/passwd`; стендовая заглушка в `tessera_verify` удалена. Отказ: встроенным и служебным принципалам, доменным и квалифицированным именам, при ошибке резолва; резолв читает только локальные данные (`NetUserGetInfo` по локальной SAM + локальные well-known SID), к контроллеру домена не обращается
- [ ] 5.10 Прогон источника класса УЗ на стенде: правила классификации покрыты тестами на моке (исполняются на macOS), но сам Win32-источник (`windows_account::os`) на Windows не исполнялся — подтверждена только компиляция под `x86_64-pc-windows-gnu`. Проверить: обычная локальная УЗ, `Администратор`/`Гость`, `система`/`LOCAL SERVICE`, встроенная группа, доменное имя, несуществующее имя
- [x] 5.4 Named-pipe сервер (поток на соединение) поверх фрейминга `tessera_proto`; дескриптор безопасности `D:P(A;;GA;;;SY)` — только SYSTEM; `FILE_FLAG_FIRST_PIPE_INSTANCE` (чужой владелец имени = отказ старта), потолок экземпляров. Дескрипторы overlapped: ожидание кадра и ожидание клиента имеют срок. Молчащий клиент получает `1101` и отключается, поток и экземпляр возвращаются в пул; остановка службы — по флагу между ожиданиями, самоподключение как способ разбудить accept-петлю удалено вместе с ожиданием, которому оно было нужно
- [x] 5.11 Два срока разведены явно (`protocol::Budgets`): бюджет рукопожатия (2 с — это срок для программы) и бюджет простоя между запросами (3 мин — это срок для человека, который выбирает роль и набирает PIN). Обработка запроса не ограничена ни тем, ни другим: пока служба ждёт носитель, чтения нет, поэтому бюджет простоя может быть короче `usb_wait`, ничего не обрывая. Зеркальная обязанность клиента (ожидание ответа должно превышать `usb_wait`) названа в доке и задана в CLI. Проверяется на macOS: молчащий до рукопожатия клиент, молчащий после рукопожатия, активный клиент, запрос медленнее бюджета простоя
- [x] 5.5 `Hello` со строгой сверкой версии; обрыв при несовпадении, при первом кадре не-`Hello`, при повторном `Hello`, при недекодируемом и oversize-кадре. Проверяется кроссплатформенно
- [x] 5.6 `ListRoles`: перечень читает служба (не клиент), порядок по `level`, затем по id; дефолтной записи нет. Нечитаемый store = `1500 INTERNAL`, а не пустой список
- [x] 5.7 `AuthenticateRequest`/`AuthenticateResult`: служба сама ищет том и читает удостоверение, зовёт `authenticate_pkcs12` через `di::wire_with_monitor`; вердикт несёт код из таблицы `FlowError::pam_code` и огрублённую категорию (media/credential/role/internal), причина целиком — только в журнале
- [x] 5.8 Hash-chain журнал в каталоге данных (ACL наследуется от protected-DACL каталога: SYSTEM и администраторы). Журнал подключён как monitor-клиент verify-пути, поэтому незаписанный журнал = отказ входа, а не тихая потеря записи
- [x] 5.9 Тестовый CLI-клиент `tessera-engine-cli` (`roles`/`auth`/`ping`) поверх общего клиентского модуля, который затем возьмёт CP. Прогон на стенде — за мной не выполнялся (развёртывание вне моей части)

## 7. Credential Provider

- [x] 7.1 Walking skeleton: COM-обвязка `ICredentialProvider`/`ICredentialProviderCredential2`, регистрация CLSID скриптом, тайл виден в LogonUI. **Подтверждено на стенде 2026-07-30**: провайдер зарегистрирован, тайл рисуется, поля на месте, ошибок Winlogon/LogonUI/COM в журналах нет. Rust-обвязка внутри процесса входа состоялась
- [x] 7.2 Panic-guard на всех COM-точках входа; краш внутри CP не валит LogonUI — `panic_guard::guard` + `PanicFlag`; пойманная паника переводит тайл в состояние «неисправен», после которого сериализации не бывает. Re-entrant вызов (занятый `RefCell`) отклоняется, а не паникует
- [x] 7.3 Решение по развилке «Rust или C++-шелл»: **Rust**. `windows` 0.62 отдаёт оба V2-интерфейса и `#[implement]`; C++-шелл не потребовался. Цена — три послабления линтов на макро-генерируемый код и прямая зависимость от `windows-core` (макрос печатает абсолютные пути)
- [x] 7.4 Поля тайла: метод (серт-носитель активен, «код» присутствует и не выбирается), роль, PIN, статус — плюс подпись тайла и кнопка отправки, без которых LogonUI нечего показать и нечем отправить
- [ ] 7.5 `GetSerialization` → `KERB_INTERACTIVE_UNLOCK_LOGON`; вход под технической УЗ состоялся. Упаковка блока написана и покрыта тестами (смещения, длины, UTF-16, отказ на слишком длинном поле); пароль приходит из вердикта службы (захардкоженного больше нет). Самого входа ещё не было — остаётся прогон на стенде
- [x] 7.6 Клиент named pipe в CP; роли в комбобоксе приходят от службы — `service::ServiceEngine` поверх `tessera_proto::Client`, транспорт за трейтом `Connector` (`PipeConnector` открывает `\\.\pipe\tessera-engine` и дублирует хендл на запись). **Условие стыковки выполнено:** обмен идёт на рабочем потоке под дедлайном 20 с, поэтому зависшая служба больше не может удержать поток LogonUI — это был отказ в обслуживании на пути логина, а не деградация. Просроченный дедлайн даёт тот же fail-closed, что и обрыв канала: статус в тайле, сериализации нет. Честная цена: просроченный поток не убивается, а бросается (держит хендл и поток до ответа службы или разрыва) — записано в доке модуля
- [x] 7.7 Вердикт до сериализации: пароль берётся из `Admission` вердикта, `StubEngine` и сборочные `option_env!`-переменные удалены целиком. Зануление после `GetSerialization` на месте; `session_id` вердикта пишется в лог для сверки с журналом службы
- [x] 7.8 Fail-closed: служба недоступна, обрыв pipe, несовпадение версии, отказ — статус в тайле, сериализации нет. Шесть транспортных ошибок (включая просроченный дедлайн и ошибку-ответ службы) и все четыре категории отказа сводятся к `CPGSR_NO_CREDENTIAL_NOT_FINISHED`; категории отказа неразличимы на экране (не оракул), дедлайн отделён от недоступности отдельным статусом — он не зависит от удостоверения. Проверено тестами на моке; на живом LogonUI — вместе с 7.1
- [x] 7.9 Unit-тесты не-COM логики: 60 тестов исполняются на macOS — таблица полей, комбобоксы, отсутствие дефолтной роли, однократность заполнения списка ролей, упаковка KERB-блока, panic-guard, все ветки `submit`, стык со службой на моке транспорта (допуск, четыре категории отказа, обрыв, несовпадение версии, ошибка службы, дедлайн) и файл лога (ротация, отказ создавать неподготовленный корень)
- [x] 7.10 Роли доходят до экрана. Прогон 2026-07-30 вскрыл разрыв: состояние наполнялось в `SetSelected`, а LogonUI читает содержимое комбобокса при построении тайла и второй раз не спрашивает — список на экране оставался пустым и неактивным. Список запрашивается при создании тайла (до того, как LogonUI что-либо прочитал) и имеет собственный короткий дедлайн 3 с, потому что это ожидание приходится на построение экрана входа, а не на действие инженера. Поздний путь оставлен для случая «служба поднялась после экрана»: `ensure_roles` сообщает, что список наполнился именно этим вызовом, и тогда `SetSelected` досылает пункты через `ICredentialProviderCredentialEvents` (`AppendFieldComboBoxItem` + `SetFieldComboBoxSelectedItem` + `SetFieldInteractiveState`). Ровно один вызов отчитывается о наполнении — иначе список удвоился бы
- [x] 7.11 Сток логов: `logging` пишет в `C:\ProgramData\Tessera\logs\tessera_cp.log` (корень берётся литералом, как в службе; каталог `logs` создаётся под уже подготовленным корнем, сам корень — никогда, иначе унаследует права `%ProgramData%`). Подписчик ставится один раз из `DllGetClassObject`. Уровень по умолчанию `debug` — намеренно подробно на время стенда, снимается `TESSERA_CP_LOG=info`. Каждая COM-точка входа пишет строку, поэтому порядок вызовов LogonUI виден из лога. Ни PIN, ни пароль, ни материал удостоверения в лог не попадают
- [ ] 7.12 Повторный прогон на стенде: список ролей на экране, статус виден при остановленной службе, лог содержит порядок вызовов LogonUI (в частности — зовётся ли `SetSelected`)
