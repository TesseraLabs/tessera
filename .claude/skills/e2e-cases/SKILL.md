# Формат кейсов e2e-реестра Tessera

Реестр `tests/e2e/cases/*.yaml` — источник истины о том, что проверяется на живой
системе. Раннер (`cargo xtask e2e`) исполняет его в контейнере или на VM.

Формат намеренно беден: четыре сорта шагов, три вида ожиданий. Как только кейсу
нужны условие или цикл — логика уходит в `tests/e2e/helpers/`, а не в YAML.

## Шаблон

```yaml
suite: auth                      # имя suite, по нему же работает --filter
description: Аутентификация по удостоверению через PAM-стек
setup: [install-package, deploy-fixtures]   # helpers/setup/<имя>.sh, раз на прогон

cases:
  - id: AUTH-001                 # уникален в пределах прогона
    title: Валидное удостоверение пускает пользователя   # формулировка ГАРАНТИИ
    requirement: openspec/specs/cert-authentication-flow/spec.md
    requires: [service-manager, usb]     # возможности профиля
    steps:
      - run: helpers/usb-loop.sh attach {{fixtures}}/leaf_rsa.p12
      - run: helpers/pam-drive certauth {{user}} authenticate
        stdin: "{{pin}}"
        expect: { exit_code: 0, stdout_matches: "auth: PAM_SUCCESS" }
        timeout: 60
      - expect_journal: { unit: tessera, matches: "auth ok" }
      - expect_file: { path: /etc/tessera/config.toml, mode: "0640" }
    teardown:                    # выполняется ВСЕГДА: провал, таймаут, Ctrl-C
      - run: helpers/usb-loop.sh detach
```

Все поля проверяются `deny_unknown_fields` — опечатка в имени поля валит загрузку
реестра, а не прогон посреди стенда.

## Справка по полям

| Шаг | Поля | Смысл |
|---|---|---|
| `run` | `run`, `stdin`, `expect`, `timeout` | команда через `sh -lc` в целевом окружении |
| `expect_journal` | `unit`, `matches` | регексп по срезу журнала за время кейса |
| `expect_file` | `path`, `exists`, `mode`, `matches` | файл в целевом окружении |
| `pause` | `pause`, `capture` | остановка с инструкцией оператору |

`expect`: `exit_code` (по умолчанию 0), `stdout_matches`, `stderr_matches` — регекспы.
Больше ожиданий нет и не будет: всё остальное — в хелпер с осмысленным кодом возврата.

**Режим кейса не пишется руками.** Он выводится: нет `pause` → `auto`, есть и то и
другое → `mixed`, только `pause` → `manual`.

Подстановки `{{user}}`, `{{pin}}`, `{{fixtures}}`, `{{helpers}}` приходят из профиля и
`~/.config/tessera-e2e/stand.toml`. **Секретов в реестре быть не должно** — только имя
подстановки.

## Ожидания измеряются, а не сочиняются

Это главное правило файла. Ожидание кейса — утверждение о продукте, а не догадка.
Каждое `exit_code`, `stdout_matches` и `matches` берётся ровно из одного из трёх мест:

1. **Фактический прогон.** Выполни команду в контейнере, посмотри код и вывод,
   зафиксируй увиденное.
2. **Код хелпера или продукта.** `helpers/pam-drive.c` возвращает PAM-код фазы
   напрямую; строки журнала ищи в `tracing::`-вызовах нужного модуля.
3. **Спека**, если она фиксирует наблюдаемое поведение дословно.

Нечем подтвердить — не пиши кейс. Заготовка с выдуманным ожиданием хуже отсутствия
кейса: она даёт `FAIL`, который выглядит как дефект продукта, и на его разбор уходит
время, пока настоящая регрессия ждёт.

**Проверено на практике:** агент, писавший кейсы без этого правила, выдал пару
`exit_code: 8` + `stdout_matches: "auth: PAM_CRED_EXPIRED"`. В Linux-PAM `8` —
это `PAM_CRED_INSUFFICIENT`, а `PAM_CRED_EXPIRED` равно `16`: ожидание противоречило
себе и не сошлось бы ни при каком поведении продукта.

### Измеренное поведение ≠ ожидание кейса

Измерение отвечает на вопрос «что продукт делает сейчас», а кейс фиксирует «что он
обещает». Обычно это одно и то же. Когда расходится — **пиши обещанное**, и пусть
кейс упадёт: `FAIL` в первом прогоне заносится в `BASELINE.md` с комментарием и живёт
там как известный долг, не мешая ловить новые регрессии.

Подогнать ожидание под фактическое поведение — значит закрепить дефект в реестре
навсегда: после этого никакой прогон о нём не скажет, потому что «эталон» и есть
дефект.

Обещанное берётся из спеки (`openspec/specs/`), а не из кода. Если код, тест и спека
согласованно утверждают одно, а внешний стандарт — другое, прав внешний стандарт:
согласованность трёх наших источников означает лишь, что ошибка была скопирована.

**Так и нашли живой дефект:** `flow.rs` возвращал на исчерпание попыток PIN код `8`
с комментарием `PAM_MAXTRIES`, юнит-тест закреплял `8`, спека писала «8 PAM_MAXTRIES».
В заголовках Linux-PAM `PAM_MAXTRIES` = `11`, а `8` — `PAM_CRED_INSUFFICIENT`. Три
согласованных источника были одинаково неправы; поймал это e2e-кейс, потому что
`pam-drive` печатает имя константы по настоящим заголовкам.

Коды `pam-drive`: PAM-код фазы напрямую (`PAM_SUCCESS` 0, `PAM_AUTH_ERR` 7,
`PAM_MAXTRIES` 11, `PAM_ACCT_EXPIRED` 13, `PAM_CRED_EXPIRED` 16), плюс служебные
`64` (ошибка аргументов) и `70` (сбой самого драйвера). Служебные перечислены в
профиле как `error_exit_codes` и дают `ERROR`, а не `FAIL` — кроме случая, когда кейс
ожидает такой код явно.

## Кейс пишется от гарантии

`title` — то, что обещано пользователю продукта и переживёт рефакторинг.

| Так | Не так |
|---|---|
| Просроченное удостоверение не пускает | `tessera check` печатает WARN про fallback |
| Отзыв через CRL закрывает доступ | Функция `validate_chain` возвращает `Err` |
| Пакет не активирует службу без конфигурации | В логе есть строка «config missing» |

В e2e-реестр идёт только то, что требует настоящей системы: установленный пакет,
живой PAM-стек, udev, служба, журнал. Остальное — unit-тесты в `cargo test`.

`requirement` — ссылка на существующее требование. Проверь, что файл и якорь на месте:
`openspec/specs/<capability>/spec.md` либо `specs/*.md`.

## requires: что объявлять

| Возможность | Есть в профилях | Когда указывать |
|---|---|---|
| `usb` | все | кейс предъявляет удостоверение с носителя |
| `service-manager` | все (`systemd` или `manual`) | кейсу нужен работающий monitord |
| `mac` | только `astra-vm` | МКЦ, МРД, ЗПС — модуля parsec в контейнере нет |
| `graphics` | только `astra-vm` | fly-dm и всё визуальное |
| `hardware-token` | только `astra-vm` | физический JaCarta или Рутокен |

Кейс, требующий недоступной возможности, получает `SKIP` с причиной — это нормально
и видно в отчёте. Занизить `requires`, чтобы кейс «прошёл» в контейнере, —
испорченное evidence.

## Teardown обязателен

Если кейс что-то подключил, смонтировал, запустил или изменил — верни как было.
Teardown выполняется при любом исходе, поэтому обязан быть идемпотентным: `detach`
на пустом месте завершается успехом.

**На VM-профиле:** изменения PAM-стеков снимаются через `integrate-pam.sh
--unintegrate` до удаления пакета. `postrm` снимает только `@include tessera*`, а
`session required pam_tessera.so` остаётся ссылаться на удалённый модуль — после чего
ломаются sudo и вход в систему.

## Частые ошибки

| Ошибка | Чем плохо |
|---|---|
| Ожидание сочинено «по смыслу» | Ложный `FAIL`, разбор впустую |
| Ожидание подогнано под факт | Дефект закреплён как эталон, прогон о нём больше не скажет |
| `pin: "1234"` прямо в YAML | Секрет в git; PIN приходит подстановкой |
| Кейс проверяет внутренности | Сломается на первом рефакторинге |
| Нет teardown после `attach` | Следующий кейс стартует на грязном стенде |
| `requires` занижен | Кейс «проходит» там, где ничего не проверяет |
| Условие или цикл в шаге | Формат не поддерживает; вынеси в хелпер |
| Новое поле «чтобы выразить кейс» | `deny_unknown_fields` не пропустит; обсуди расширение отдельно |

## Проверка перед сдачей

```bash
cargo test -p xtask                      # реестр грузится, профили валидны
cargo xtask e2e --profile ubuntu-container --filter <SUITE> --recreate
```

Кейс считается готовым, когда прогнан и его результат осознанно занесён в
`tests/e2e/BASELINE.md`. Ненаблюдавшийся кейс — не evidence.
