# Вход по USB-носителю

## Purpose

Причинность входа от появления носителя до вердикта PAM. Процессная страница
существует потому, что причинность здесь пересекает несколько сущностей и
внешнего участника (носитель, оператор); внутри одной сущности хватило бы её
собственных норм.

## Шаги

Один причинный шаг на пункт. Ссылка на следующий шаг явная; исходы перечислены
отдельно от шага.

1. **Предъявитель вставляет носитель.** Инициатор — человек, шаг внешний.
   Дальше → шаг 2.
2. **Модуль монтирует носитель и читает PKCS#12-конверт.**
   Целевая сущность — [[auth.credential|удостоверение]]. Дальше → шаг 3.
3. **Модуль запрашивает PIN, бюджет — три попытки.**
   Дальше → шаг 4. Исход «бюджет исчерпан» — ниже.
4. **Модуль доказывает владение ключом (challenge-response).** Дальше → шаг 5.
5. **Модуль строит [[auth.trust-chain|цепочку доверия]] из конфигурации.**
   Материал берётся только из [[auth.device-config|конфигурации устройства]]
   ([[auth.ADR-003]]). Дальше → шаг 6.
6. **[[auth.revocation-check|Проверка отзыва]] устанавливает статус.**
   Дальше → шаг 7. Исходы «отозвано» и «статус неопределим» — ниже.
7. **Модуль сверяет `pam_cert_host_binding` с [[auth.host-identity|идентичностью устройства]].**
   Дальше → шаг 8.
8. **Модуль сверяет запрошенную [[auth.role|роль]] со списком в удостоверении.**
   При успехе возникает [[auth.authentication-proven|факт доказанной аутентификации]].
9. **[[auth.session-registration-policy|Политика регистрации сессии]]** передаёт
   команду [[runtime.open-monitored-session|открытия контролируемой сессии]] через
   [[runtime.pam-monitord-ipc|IPC-контракт]]. Результат команды и настроенный
   fail mode определяют окончательный PAM-вердикт.

## Исходы

Основной, отказ и таймаут описаны обязательно: шаги 1–3 идут через человека и
съёмный носитель, поэтому категория «не дождались» здесь применима и
`not-applicable` для неё не заявляется.

### Успех
Проверки удостоверения пройдены, а политика регистрации либо получила
подтверждение monitord, либо допустила транспортный отказ в `permissive` mode.
Сессия открывается под запрошенной ролью. Носитель размонтируется сразу по
завершении фазы аутентификации: ключ уже использован, `.p12` больше не нужен.
Регистрация monitord входит в процесс до окончательного вердикта: в `strict`
mode её отказ закрывает вход, в `permissive` обычная транспортная ошибка не
отменяет уже доказанное право.

### Отказ по существу
Удостоверение отозвано, привязка к устройству не совпала, роль вне списка либо
цепочка не построена. Вход отклоняется, причина различима в журнале и в коде
возврата PAM.

### Отказ по неопределимости
Статус отзыва установить не удалось ([[auth.revocation-check]] → `REV-002`),
конфигурация невалидна, идентичность устройства не резолвится либо strict-policy
не смогла зарегистрировать контролируемую сессию. Вход отклоняется.
Отличимость этого исхода от предыдущего — требование
[[auth.fail-closed]] `FC-002`, без неё эксплуатация неотлаживаема.

### Исчерпание бюджета попыток
PIN не введён за три попытки. Возвращается `PAM_MAXTRIES`, а не общий код
ошибки: приложение обязано отличить исчерпанный бюджет от проблемы с доступом
к данным аутентификации и прекратить дальнейшие запросы.

### Таймаут ожидания носителя
Носитель не появился за отведённое время. Вход отклоняется как неопределимость:
отсутствие носителя не доказывает права входа.

## Компенсация

Отсутствует и не требуется: до открытия сессии процесс не оставляет наблюдаемых
следов, кроме записей журнала. Монтирование снимается guard'ом на любом пути
выхода, включая ошибочный.
