# Tessera — правила работы в репозитории

## Кейс раньше кода

`tests/e2e/cases/*.yaml` — реестр гарантий продукта на живой системе. Он
находит то, чего не находят юнит-тесты. Поэтому:

- **Дефект чинится только после того, как написан воспроизводящий его кейс.**
  Ожидание в кейсе — правильное поведение, не текущее. Кейс обязан быть красным
  до правки кода: зелёный с первого раза значит, что он не воспроизводит дефект.
- **Новая функциональность приезжает вместе с кейсами** — изменение Spec9 и
  кейсы рассматриваются как одно изменение домена.
- **Каждый кейс несёт `requirement: spec9:<ID>`** — стабильный ID приватной
  нормы, чью гарантию он стережёт. Публичный репозиторий проверяет форму ID,
  а приватный workspace — существование нормы и обратный evidence-якорь.
- **Стенда нет — кейс всё равно пишется**, а прогон откладывается: красный кейс
  заносится в `BASELINE.md` с одной строкой почему. `BASELINE.md` описывает
  наблюдаемое состояние, а не желаемое; править его руками, чтобы «стало
  зелено», нельзя.
- **Кейс невозможен или не нужен** (документация, рефакторинг без изменения
  наблюдаемого поведения, нет профиля под проверку) — сказать вслух и записать
  причину в `tests/e2e/.e2e-ack`.

Формат кейсов — `.claude/skills/e2e-cases/SKILL.md` (читать его, а не
`crates/xtask/.../registry.rs`). Процесс — навык `e2e-first`.

Прогон: `cargo xtask e2e --profile <profile> [--filter <suite>] [--update-baseline]`.
`.deb` для прогона берётся `gh run download` для нужного коммита main — локальная
сборка проверяет не тот код.

## Правки кода

Rust правится через субагента `rust-pro`, не напрямую. После изменений —
`cargo clippy --all-features` и `cargo clippy` без фич: CI линтит только первое,
и дефолтная сборка успевала быть красной незамеченной.
